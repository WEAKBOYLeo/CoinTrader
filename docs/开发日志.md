### 当前问题（按严重度）

1. **【阻塞 M4 核心交付】信号源未接线**。
   `cmd_live_run` → `build_live_context` 没有注入 `signal_provider`，默认空 → 服务只空转对账，**永远不会开仓**。M4 要求真实「开仓→部分成交→平仓→重启恢复」闭环，没有信号源则 7 天长跑只是稳定性测试。
   待决策：实现最小信号源（接 scanner，周期扫描资金费率 → top-N → canary 10U 生成 Signal）或先空转观察。

2. **【环境】demo 合约端点无官方文档**。`demo-fapi.binance.com` 来自社区项目，端点能力有缺口（无 GET leverage、user stream 20s 断开、参数大小写敏感）。行为靠实测补齐，币安未来可能调整。

3. **【环境】依赖 mihomo 日本-5 节点**。节点坏或切换会导致读请求失败（已有 5 次重试缓冲），但持续劣化会使 poll 流 untrusted → RECOVERY。建议长跑期间不动该策略组。

4. **【设计限制】poll 模式成交感知延迟**。demo 无用户流，成交/撤单靠 5s 轮询 + 30s 对账发现，比 WS 模式延迟高。M4 的延迟/滑点报告需标注该差异；M6 主网 canary 必须回到 stream 模式。

5. **【既有、未修】RECOVERY 不自动解除**。进入 RECOVERY 后只能重启恢复（设计 §7.3 有意为之）。长跑 7 天期间若发生瞬时故障进 RECOVERY，需要人工介入重启。可考虑增加「对账 N 次通过 + 流新鲜 M 秒」的自动恢复路径（需谨慎，属于安全闸门变更）。

6. **【小】`live doctor` 不覆盖 demo 端点差异**（如 410/20s 断流），目前靠运行时日志发现。

### 下一步（建议顺序）

1. 决策并实现最小信号源（问题 1），验证首笔 canary 开仓闭环（10U，1x，isolated）。
2. 手动演练：kill 进程重启 → 启动恢复对账；`touch KILL_SWITCH` → 停机验证。
3. 7 天长跑 + 每日检查（对账一致性、RECOVERY 次数、轮询失败率）。
4. 跑满后出 M4 报告：延迟/滑点/拒单/流稳定性 + 对账差异记录。
5. 通过后才能进入 M5（Shadow/Paper 14 天）。

### 测试中发现并修复的真实 Bug

1. `executescript` 隐式 COMMIT 与外层迁移事务冲突 → `_migrate_1` 拆成逐条 `execute`（`_split_sql` 按顶层分号拆分）。
2. `funding_cashflows` 表无 `ts_ms` 列，`_query_table` 默认 `ORDER BY ts_ms` 报 `no such column` → per-table 时间列映射补 `funding_cashflows→funding_ts_ms`。
3. PnL 未平仓 round-trip 的资金费窗口右端误用开仓 pair 的 `completed_ts_ms`（=开仓时刻），导致开仓后已结算资金费被排除 → 未平仓时右端改为当前时刻（仍不用未来数据）。
4. 脱敏正则 `X-MBX-APIKEY[:\s]\S+` 匹配不到 `X-MBX-APIKEY: <value>`（冒号后带空格）→ 改 `X-MBX-APIKEY[\s:]*\S+`。
