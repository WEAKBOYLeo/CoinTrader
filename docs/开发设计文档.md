# CoinTrader 实盘开发设计文档

- **项目**：CoinTrader
- **目标**：在不破坏现有研究、回测和安全隔离的前提下，实现 Binance 现货 + USDⓈ-M 永续资金费率套利的可恢复实盘执行。
- **文档状态**：目标架构与验收基线；不是现状证明，也不授权任何真实下单或主网放量。
- **编写时间**：2026-09-18；本次现状核对：2026-09-23
- **目标交易所**：Binance Spot + USDⓈ-M Futures
- **核心原则**：先验证执行系统，再验证小额实盘；主网不是测试网的“换一个 URL”。

> 本文只定义开发路线和验收标准，不代表策略已经盈利，也不构成投资建议。任何阶段都不能把历史回测收益当作未来收益保证。

## 1. 结论摘要

项目已有若干实盘系统核心组件，但不能仅凭代码结构、测试通过或能提交订单，就判定为“完整且稳定的交易系统”。当前基础包括：只读公开行情客户端、磁盘 JSON 缓存、共享限流协调器、scan epoch、SQLite 账本与账户投影、订单计划、双腿执行状态机、用户流/REST 对账、CLI/WebUI 监控及广泛离线测试。

仍须以真实生产装配与运行证据验证以下闭环：历史数据是否按区间命中本地并只补缺口；实时 Spot/Perp 报价是否来源明确、时间对齐且过期拒绝开仓；同出口 IP 的外部流量是否纳入限流余量；生产服务是否从策略目标一路经过持久化意图、风险审批、订单计划、执行和对账；重启、断流、限流、部分成交后是否安全恢复。当前 `LiveService` 仍持有不少生命周期/业务状态，`MarketDataService` 由 scan epoch 构造行情契约而实时双腿报价另走 live 路径，WebUI 仍混合账本与服务内存快照。因此结论是：**架构基础较完整，具备继续验收和小范围验证的条件；尚不能据静态检查认定稳定实盘已闭环。**

建议路线：

```text
研究结论
  -> 交易意图层
  -> 签名 REST + 规则校验
  -> 订单状态账本
  -> Spot/Futures 用户数据流
  -> 重启对账与故障恢复
  -> testnet 端到端
  -> paper/shadow 长时间运行
  -> 极小名义额主网 canary（单独人工批准）
  -> 逐步放量（每次单独批准）
```

**不得直接把现有环境变量改成主网并运行策略。** 主网启动必须通过独立的 live profile、人工确认、IP 白名单 API Key、单实例锁、对账通过和 canary 验收。

## 2. 现有系统与目标差距

### 2.1 已有能力

- `data/` 只读公开 API，避免数据层获得签名和下单能力。
- `research/` 和 `backtest/` 保持研究与实盘执行隔离。
- `execution/guard.py` 提供运行时安全闸门和审计能力。
- `RateLimitCoordinator` 已供公开/签名客户端共享注入，支持 Spot/Futures scope、优先级、保留预算、响应头观测及 429/418 状态。
- `DiskCache` 支持 JSON 磁盘缓存、TTL、稳定参数键和原子替换；若干历史/静态端点已接入缓存。
- `MarketDataSynchronizer` 用 scan epoch 固定候选 universe 与 cutoff，并以 READY/DEGRADED/EXPIRED 约束候选数据。
- SQLite 已有策略/intent/risk/plan 记录、订单/成交、账户/持仓快照、current projection、同步游标和对账能力。
- `OrderPlanner`、`PairExecutor`、用户流、未知提交查询和启动/周期恢复已有实现与测试。
- CLI/WebUI 可展示账户、订单、限流、行情就绪度和运行指标，但部分健康状态仍来自 LiveService 内存快照。

### 2.2 尚未由现有组件自动保证的事项

| 能力 | 现有基础 | 尚需证明/改进 |
|---|---|---|
| 历史行情复用 | 磁盘缓存、资金费/K 线接口缓存 | 缓存键按整段参数划分，不等价于任意区间覆盖索引；需证明缺口检测、续拉、离线数据集完整性与修订处理 |
| 实时报价 | 实时 REST 获取、scan epoch 市场数据质量、短 TTL 部分缓存 | epoch 中的资金费/成交额快照不等于订单时刻双腿报价；报价来源、时差、最大年龄必须贯穿策略到下单计划 |
| 限流稳定性 | 单进程共享协调器、响应头观测、优先级与冻结 | 不能控制同出口 IP 的其他进程；观测竞态/无响应头仍可能 429；因此不能承诺“不触发限流”，只能做到降概率、退避、熔断和告警 |
| 策略合理性 | 纯 evaluator、无前瞻测试、成本/基差研究 | 策略收益不是工程架构可保证的；需用保守成本、压力情景、样本外与 paper/shadow 的实测偏差验收 |
| 下单闭环 | 规则归一、批准意图、计划化 pair 执行及状态账本 | 必须持续确认生产入口无旁路，submit/timeout/partial/compensation 和成交账本顺序都有故障注入证据 |
| 控制台监控 | CLI/WebUI、只读查询和指标 | 关键值要显示模式、时间、来源、权威等级；UNKNOWN 不得伪装成 0/RUNNING；WebUI 不应成为交易主链依赖 |
| 长期运行 | watchdog、systemd 部署约定、恢复/对账测试 | 单测不能代替 7 天以上的持续运行、重启演练、磁盘容量/备份和告警响应演练 |

### 2.3 必须修正的现有假设

| 假设 | 风险 | 目标设计 |
|---|---|---|
| 有磁盘缓存就表示行情已完整持久化 | TTL 缓存可能只有单次查询结果，未必覆盖缺失区间或支持增量恢复 | 区分缓存、历史数据集、交易账本；维护区间覆盖元数据并只补缺口 |
| 有共享限流器就不会 429 | 协调器只管本进程；同一出口 IP 其他程序和并发响应会造成未观测消耗 | 使用权重响应头、保守预算、共享 IP 监测、429 冻结/有限重试/告警；不承诺零 429 |
| scan epoch 就是下单报价 | epoch 用于候选分析/因果 cutoff；订单前价格还须重新获取 | 分开研究快照、候选横截面和订单前双腿报价，分别校验 freshness/skew |
| 订单 HTTP 成功就代表 pair 完成 | 可能部分成交、用户流延迟、另一腿失败 | 以交易所订单状态、实际成交、持仓和账本对账判定完成 |
| WebUI 展示正常就等于交易状态可信 | UI 可能显示旧的内存字段或读模型 | 每个值展示更新时间、来源和权威性；交易安全由同步风控与状态机决定 |
| 单元/静态测试通过就可以主网 | 无法覆盖代理、网络、交易所行为和长期运行 | 分层执行 mock、paper/shadow、testnet、长跑和经批准的 canary |

## 3. Binance API 与行情治理

Binance 接口、参数、权重和限额会变更。上线前核对官方文档与响应头实测；端点权重明细维护在 `docs/API限流规则.md`，避免此文重复陈旧数据。

### 3.1 认证与签名

继续保持签名实现隔离：按接口规范生成 timestamp/recvWindow/HMAC；不记录原始认证 payload、Secret、完整认证 URL 或 signature。签名参数顺序和 URL 编码必须有测试。凭证仅从环境变量或受控凭据注入。

### 3.2 请求调度与限流

所有公开与签名客户端在 live 生产装配中注入同一个 `RateLimitCoordinator`。Spot 与 USDⓈ-M Futures 分属独立 scope。当前优先级语义为：

```text
P0  下单、撤单、紧急减风险；critical 请求不自动重试
P1  启动恢复、对账、未知订单查询
P2  已有仓位所需账户/市场刷新
P3  候选刷新和普通行情
P4  历史回填
```

规则：

- 每次请求 acquire permit，每次响应观测 `x-mbx-used-weight-1m`；无响应头时保守本地记账，未知端点使用保守权重并记录诊断。
- P0/P1 使用保留预算；P2 受软限；P3/P4 受扣除保留预算后的低优先级额度限制。
- 429 按 scope 冻结并尊重更长的 `Retry-After`；冻结期间不探测。只读请求可有限退避重试，critical 请求交由查询/恢复流程处理。
- 418 进入封禁/停机处置，禁止普通请求继续发送；触发控制状态与人工可见告警。
- 订单请求的 408、网络超时、5xx 都可能是 `UNKNOWN_SUBMISSION`；先按 `clientOrderId` 查询，不盲目重发。普通只读请求可有限重试。
- 认证、签名与时钟错误不按普通网络错误重试；校时或停交易并告警。
- 协调器是进程内治理，不控制同一出口 IP 的其他进程或机器。响应头虽能反映服务端已用量，观测间隙/并发仍有竞态，因此共享 IP 下不能保证绝不触发 429。
- 监控暴露 scope、已用/上限、in-flight、等待队列、冻结/封禁和错误次数；监控不得直接请求交易所。

### 3.3 数据保存、缓存和复用

当前 `DiskCache` 是带 TTL 的 JSON 磁盘缓存，包含参数哈希键和原子写。其价值是减少相同请求、支持重复运行和部分离线研究；它**不是**带完整覆盖索引的行情仓库，也不意味着所有实时价格都已落盘。设计按数据性质分层：

| 数据 | 保存策略 | 使用边界 |
|---|---|---|
| 已闭合 K 线、已结算资金费 | 按 market/symbol/interval/时间段保存；元数据记录覆盖区间、来源、抓取时间和 schema 版本；任务重跑先读本地，仅补缺口/未闭合尾段 | 可供研究/回测离线复用；交易所修订需版本或明确重取策略 |
| exchangeInfo、funding interval | 有 TTL 的磁盘缓存；刷新失败时保留旧值仅供诊断 | 下单规则过期/缺失时禁止新单；结算周期缺失不得默默套错误周期 |
| 全市场 ticker/universe | 单次全市场端点优先，适合 TTL 缓存 | 仅用于候选/成交额筛选，不替代提交前报价 |
| 当前 mark/spot/perp quote | 连续行情优先 WebSocket；当前实现可按短 TTL REST，所有请求受共享调度器约束 | 记录 exchange/receive timestamp、来源和连接代次；过期、断流、超时差时禁止新增风险 |
| 订单、成交、资金费收入、账户和持仓 | SQLite 账本/投影，交易所 id 幂等；不放入可随意清理的研究缓存 | 当前账户事实以交易所完整 capture 和对账校准 |

缓存要求：读写失败、损坏、schema 不兼容、磁盘满均有指标/告警；缓存损坏可按 miss 重拉，但不能悄悄把不完整数据标为完整。缓存目录要有保留/清理、容量告警和备份策略。持久化历史若不覆盖请求区间，明确报告缺口并补拉，不能以 TTL 未过期推断区间完整。

### 3.4 数据因果与新鲜度

候选研究、回测数据和订单即时报价是不同用途的数据，必须保留不同的时间语义。scan epoch 固定 universe/cutoff；只纳入 cutoff 前已闭合 K 线和已结算 funding。下单前重新取得 Spot/Perp 报价，记录来源、exchange timestamp、receive timestamp、报价年龄及两腿时间差；订单计划的有效期不得超过报价/批准意图有效期。新开仓只接受完整、有效、新鲜且时间对齐的数据。历史缓存不能拿来当当前价格。

状态至少区分：`FRESH`、`STALE`、`INCOMPLETE`、`INVALID`、`DEGRADED`。故障时禁止新增风险；减风险须使用明确标记的风险控制报价策略，不得伪造有效快照。

## 4. 目标架构与生产主链

采用模块化单体，不为当前规模引入微服务、Kafka 或 Redis。目标主链：

```text
Market facts
  -> StrategyProposal / TargetPortfolio
  -> PortfolioIntent (先持久化、幂等)
  -> RiskDecision (同步审批并持久化)
  -> ApprovedIntent
  -> ExecutionPlan (Decimal 规则归一并持久化)
  -> PairExecutor
  -> Order / Fill / Account events
  -> SQLite ledger + current projections
  -> Reconciliation + read models
```

职责边界：

- `domain/`：不可变契约、校验，无 IO。
- `data/`/Binance adapters：协议转换、网络与限流，不做策略决策。
- `market_data/`：数据质量、缓存/历史存储、cutoff、新鲜度。
- `account/`：账户/仓位投影，完整 capture 才更新可信当前状态。
- `strategy/`：纯计算，只产目标/理由，不创建订单。
- `portfolio/`：目标与实际仓位差异，生成幂等 intent。
- `risk/`：同步审批，开仓/增仓与减仓权限区分。
- `execution/`：只处理批准计划，维护订单/pair 状态、未知提交恢复和补偿。
- `ledger/`：追加记录和投影；交易关键写失败必须 fail closed。
- `reconciliation/`：交易所快照对账；不一致时阻止开仓。
- `application/`：唯一生产装配/编排 owner；迁移期 `LiveService` 可以作 facade，不应继续扩张职责。
- CLI/WebUI/reporting：读模型查询。WebUI 可显示即时健康投影，但须标成内存/非权威来源，不能覆盖账本事实或影响执行安全。

`data/research/backtest` 不能依赖 `execution`。策略/查询层不能持有 Binance client 或 broker 能力。实际代码目前尚有兼容路径和内存快照，因此以上是目标约束，须以调用图/集成测试验收。

## 5. 运行模式、账户状态与账本

### 5.1 运行模式

```text
PAPER      本地模拟，不发私有写请求
SHADOW     真实行情/可选只读账户输入，只记录目标和风险，不提交订单
TESTNET    测试网订单，独立凭证/存储路径
LIVE       主网订单，额外人工审批与所有门禁通过
```

默认必须为 PAPER/DRY_RUN，不能因环境变量缺失进入真实下单。模式、API host、凭证类别、数据库路径和可否下单在启动摘要与控制台明示。现有三重主网闸门不得削弱：`COINTRADER_TRADING_ENABLED=YES_I_AM_SURE`、`COINTRADER_USE_TESTNET=false`、`--confirm-live`，并保留 `KILL_SWITCH` 的拒单语义。

### 5.2 账户事实与对账

交易所是当前账户/持仓/开放订单事实源；本地账本是本系统决策、命令及已观察事件的审计事实源。REST 完整 capture 用于启动、恢复与周期校准；Spot/Futures 用户流用于及时更新；断线、过期、乱序或解析失败后必须 REST 对账。capture 必须带 snapshot id、开始/结束时间、source、complete。部分 capture 不可覆盖可信 projection，状态转 UNKNOWN/STALE 并禁止新开仓。

对账至少覆盖余额、持仓、开放/未知订单、最近成交、资金费 income 和未终结 pair。结果 `CONSISTENT`、`CONSISTENT_WITH_REPAIRS`、`MISMATCH_BLOCKING` 或 `UNKNOWN`；后两者禁止新增风险。修复动作保留审计记录。

### 5.3 SQLite 账本

继续使用 SQLite，不做无必要的完整 event sourcing 重写。交易意图先落账再提交；订单命令、响应、成交、pair 状态、风险决定、账户/持仓快照、对账、安全状态和人工命令需要可关联、幂等、可恢复。交易所 id/client id 建唯一约束；Decimal 以文本保存、时间以 UTC 毫秒保存；数据库绝不存密钥/签名。关键账本写失败时停止新增风险，不能继续无审计下单。

## 6. 策略与组合分析

策略合理性与交易工程安全分开验收。策略纯计算接收明确 cutoff 的市场/账户/组合输入，产出目标组合和可解释决定；不得直接调 API 或产生订单。资金费率年化依据真实结算周期；入场过滤、退出、最大持仓、成交额流动性、基差、交易费用、滑点、资金占用均需纳入回测/压力场景。所有决定含 snapshot/dataset id、strategy version、config hash、cutoff、指标、阈值、reason 和有效期。拒绝/跳过也落账，确保可解释“为什么没交易”。

组合规划将目标转换为与交易所确认持仓的差异，考虑活动订单、可用余额、pair/gross exposure，保证先减后增且幂等。策略回测和实盘保持相同输入语义，不得使用 cutoff 后数据。历史收益不能证明未来盈利；至少报告样本外、悲观成本、基差不利场景、最大回撤和破产/极端波动情景。

## 7. 风控设计

风控不是监控。任何新增/改变风险的 intent 均在同步路径由 RiskKernel 审批；输入快照缺失、过期、账户不完整、对账失败、限流封禁、账本不可写或系统状态不允许时 fail closed。

风控至少检查：模式/权限/时间/规则/单实例锁；市场数据 quality、年龄和腿间 skew；订单精度、名义额、滑点、订单速率和重复 intent；pair/gross/symbol exposure、余额、保证金率；裸腿名义额/持续时间、hedge ratio、basis、日亏损；用户流、对账、账本、API 限流与 kill switch。

分别记录 `pair_notional`、`gross_leg_notional`、`margin_usage`、`unhedged_notional`，不可混用。开仓、增仓、换仓与 reduce-only 平仓具有不同权限。

运行状态至少：

```text
STARTING -> RECOVERY -> RUNNING
RUNNING -> DEGRADED / CLOSE_ONLY / RECOVERY / HALTED
任意运行态 -> STOPPED
EMERGENCY_FLATTEN 仅由明确人工命令触发
```

`HALT_NEW_RISK` 拒绝开仓/增仓/换仓扩大风险，允许经检查的撤单或 reduce-only；`EMERGENCY_FLATTEN` 是显式、人工、逐步审计的事故流程，不默认盲目市价平所有腿。删除 `KILL_SWITCH` 不自动恢复；恢复需重新预检、用户流稳定、完整对账和人工确认。

## 8. 双腿订单执行

目标为现货多头 + Futures 空头。执行只接受有效 `ApprovedIntent`/`ExecutionPlan`；Spot/Futures 各自按市场规则用 Decimal 对齐，检查 `tickSize`、`stepSize`、`minQty`、`MARKET_LOT_SIZE` 和 min/max notional。归一化后零量、超限或两腿不匹配时本地拒绝。client order id 对 intent/leg 稳定且唯一。

```text
NEW_INTENT -> PRECHECK -> SUBMIT_PERP -> ACK/PARTIAL/FILLED
            -> SUBMIT_SPOT_FOR_CONFIRMED_EXECUTED_QTY
            -> HEDGE_VERIFIED -> COMPLETE

提交超时/5xx -> UNKNOWN_SUBMISSION -> 按 clientOrderId 查询
部分成交 -> 只以确认累计成交量补另一腿
一腿失败 -> 补腿/补偿减风险；无法安全恢复 -> CLOSE_ONLY/HALTED + 人工告警
```

两个 HTTP 200 不能证明 pair 完成。完成判定需最终订单状态、实际成交、手续费、持仓/余额、hedge ratio 与账本对账一致。下单不得盲重试；平仓数量来自交易所实际持仓，Futures 必须 reduce-only/等价 close-position 语义，不得反向开仓。

订单类型须依据盘口深度、滑点和实测执行选定。MARKET 不是成交价保证；LIMIT+IOC 也需处理未成交残量、撤单未知和补偿流程。主网 canary 不得因为 testnet 正常而放大。

## 9. 启动、重启和恢复

启动顺序：

```text
1. 加载非敏感配置并显示运行模式
2. 验证凭证存在性/权限边界（不打印秘密）
3. 校准 server time，检查本机时钟
4. 加载/校验交易规则
5. 打开数据库并取得单实例 lease
6. REST 完整 capture（账户、持仓、开放订单）
7. 回补订单/成交/funding facts 并运行对账
8. 检查未知订单、裸腿、未终结 pair
9. 启动用户流并等待新鲜稳定
10. 等待行情横截面 READY 且订单前报价机制正常
11. 完成全部风险门禁后方可进入 RUNNING
```

进程重启、流断线/过期/乱序、未知提交、账本错误、capture 不完整、规则变化、对账差异、418、认证/签名/时钟错误都进入 RECOVERY 或更严格状态。停止策略新意图，查询交易所当前事实，先恢复未知订单与裸腿；只有一致、新鲜、账本可写、用户流健康且人工确认后恢复新增风险。

## 10. CLI、WebUI 与控制台监控

必须一眼可见运行模式、安全状态、当前账户/持仓更新时间、行情 READY/年龄/coverage、Spot/Perp 报价来源与 skew、限流 scope/used/soft cap/queue/freeze/429/418、策略最近决策、风险拒绝原因、活动订单/未知订单、pair hedge ratio/裸腿金额/持续时间、对账状态、余额/保证金、PnL 口径、DB/磁盘/进程健康。

每个值标 `as_of`、source 和权威级别（交易所确认、本地账本、内存健康观测、估算）。未知显示 UNKNOWN，不显示成零；估算 PnL 不混入 authoritative PnL。控制台和 WebUI 必须查询只读 read model；WebUI 故障不能阻断交易。控制命令走受审计的 Control Plane，不允许 UI 直接调 broker。

至少提供 overview、portfolio/pairs、orders/fills、risk/decisions、reconciliation、PnL、alerts 页面/CLI 查询。停机、恢复、人工接管指令需在 RUNBOOK 中演练维护。

## 11. 测试与运行验收

每次变更维持项目硬门禁：

```bash
uv run pytest
uv run ruff check .
uv run mypy
uv run cointrader doctor
```

保留 `tests/test_safety.py` 与 `tests/test_no_lookahead.py` 为硬闸门。故障注入覆盖：HTTP 429/418/Retry-After/缺响应头/并发窗口，读重试与 critical 不重试；历史缓存命中、缺段补拉、缓存损坏、磁盘写失败；实时行情断流/陈旧/skew；下单前断网、接收后响应超时、部分成交、一腿拒单、重复/乱序用户流、数据库失败、重启时开放单/裸腿、规则变化、时钟偏差。

验收重点不是异常被捕获，而是无重复订单、无无限重试、无静默裸腿、无不完整账户放行、无过期行情新开仓；不能自动安全恢复就进入人工接管。Mock 和离线测试不能证明交易所实测性能或长期稳定性。

## 12. 分阶段实施与准入

以下是目标迁移顺序，不是已完成状态。阶段只有在生产装配真实使用且验收证据归档后才可标完成。

### M0：当前基线与模式安全

核实调用图、主网闸门、数据库 schema、运行模式和部署配置。验收：生产入口与所有旁路有静态测试，设计文档不把目标写成现状。

### M1：行情、缓存与限流

定义历史区间存储/补缺口、短 TTL 实时报价来源、新鲜度、cache failure 语义、容量/清理/备份，以及同 IP 外部流量边界。验收：离线缓存复用与缺口测试、REST/WS 报价陈旧闸门、429/418 并发故障注入通过；Web/CLI 可看到限流状态。

### M2：账户投影与读模型

完整 capture 原子更新 current projection；WebUI/CLI 查询收敛到 QueryService；健康内存指标明确标注来源。验收：断流/重启/部分 capture 后状态可信或明确 UNKNOWN，查询不调用交易所/执行器。

### M3：策略与组合

策略目标、组合差异、拒绝原因、输入快照和 cutoff 可重放。验收：no-lookahead、重复 intent、换仓顺序和悲观成本测试通过；不因回测盈利结论弱化风险。

### M4：风险与执行闭环

所有生产 intent 经风险审批，订单只从批准计划产生；故障恢复基于交易所确认事实。验收：旁路静态禁止、订单/账本原子性边界清楚、部分成交和未知提交演练通过。

### M5：paper/shadow 与 testnet

在不触碰主网的条件下验证模式隔离、真实行情读取、执行模拟/testnet、事件回放、重启恢复和告警。

### M6：长跑及主网 canary 准入

至少建议连续 7 天运行；策略/资金费周期要求更长时延长。期间无未解释对账差异、重复订单、静默 stale data、未处置裸腿；重启、断流、限流、磁盘告警、人工停机恢复都完成演练。主网 canary 仍需单独人工批准、独立 Key/IP 白名单、最小可行名义额和逐笔复核；本设计验收不自动授权 live 或放量。

## 14. 不做的事情

- 不做多交易所路由、提现、自动转账、自动补保证金或动态加杠杆。
- 不做无限重试或把 timeout 当作确定未成交。
- 不只依赖 WebSocket、轮询或本地账本中的单一事实源。
- 不把 testnet 成功当作主网安全证明。
- 不在策略亏损时自动放宽阈值、提高杠杆或关闭停机机制。
- 不引入与当前规模不匹配的微服务、Kafka/Redis 集群。

## 16. 最终验收标准

实盘开发完成不是“能发出一笔订单”，而是：

> 在订单部分成交、响应超时、用户流断线、进程重启、规则变化、API 限流、缓存/数据库故障和交易所错误发生时，系统都能避免重复下单，准确知道实际持仓；不能自动恢复时停止新增风险并给出可执行的人工接管信息。历史数据能按区间命中本地持久化并只补缺口；实时报价来源和时间可验证，过期报价不参与新开仓；共享限流与外部流量风险可观测且有熔断恢复路径。

只有分阶段验收通过、paper/shadow 与 testnet 长跑有证据，且主网 canary 独立人工审批并完成开平仓闭环后，才允许讨论放量。
