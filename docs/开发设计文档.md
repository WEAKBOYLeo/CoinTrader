# CoinTrader 实盘开发设计文档

- **项目**：CoinTrader
- **目标**：在不破坏现有研究、回测和安全隔离的前提下，实现 Binance 现货 + USDⓈ-M 永续资金费率套利的可恢复实盘执行。
- **文档状态**：设计稿，未授权任何真实下单。
- **编写时间**：2026-09-18
- **目标交易所**：Binance Spot + USDⓈ-M Futures
- **核心原则**：先验证执行系统，再验证小额实盘；主网不是测试网的“换一个 URL”。

> 本文只定义开发路线和验收标准，不代表策略已经盈利，也不构成投资建议。任何阶段都不能把历史回测收益当作未来收益保证。

## 1. 结论摘要

当前项目还不能直接切换到实盘。原因不是缺少一个 `trade` 命令，而是缺少完整的交易系统能力：

- `src/cointrader/execution/broker.py` 只有 `SimulatedExchange`，没有真实 REST 适配器、签名和订单查询。
- 没有订单状态机，无法可靠处理部分成交、网络超时、重复提交和交易所返回未知状态。
- 没有 Spot 与 Futures 的用户数据流，没有事件恢复和断线后的 REST 对账。
- `RiskState` 是进程内对象，重启后无法从交易所恢复真实余额、持仓、订单和成交。
- 当前双腿逻辑以固定 `quantity` 作为两腿数量，没有按实际 `executedQty` 处理部分成交。
- 当前风控以 `float` 和静态配置为主，尚未纳入可用余额、保证金率、未实现盈亏、手续费、资金费和实时基差。
- 当前 `KILL_SWITCH` 会拒绝所有订单；实盘事故处理中必须区分“停止开新风险”和“允许只减仓平仓”。

建议路线：

```text
研究结论
  -> 交易意图层
  -> 签名 REST + 规则校验
  -> 订单状态账本
  -> Spot/Futures 用户数据流
  -> 重启对账与故障恢复
  -> testnet 端到端
  -> paper/shadow 长时间运行
  -> 极小名义额主网 canary
  -> 逐步放量
```

**不得直接把现有环境变量改成主网并运行策略。** 主网启动必须通过独立的 live profile、人工确认、IP 白名单 API Key、单实例锁、对账通过和 canary 验收。

## 2. 现有系统与目标差距

### 2.1 已有能力

现有项目已经具备适合继续扩展的基础：

- `data/` 只读公开 API，避免数据层获得签名和下单能力。
- `research/` 和 `backtest/` 纯计算、无网络依赖，保留了较好的可测试性。
- `execution/guard.py` 提供默认拒绝、交易开关、停机文件和审计日志。
- `execution/risk.py` 已有订单名义额、总敞口、单币种敞口、日亏损、裸头寸、基差检查。
- `secrets.py` 已将凭证与配置分离，并避免在 `repr` 和日志中输出明文。
- 回测已明确现货多头 + 永续空头的资金费率套利结构。

### 2.2 必须修正的现有假设

| 现有假设 | 实盘问题 | 目标设计 |
|---|---|---|
| `SimulatedExchange` 返回完整成交 | 真实订单可能部分成交、拒单、延迟或状态未知 | 以订单事件和 REST 查询得到的实际成交为准 |
| 两腿都用相同 `quantity` | Spot LOT_SIZE、Futures LOT_SIZE、合约面值和精度可能不同 | 用规则归一化后的每腿数量；按实际成交量记录 hedge ratio |
| REST 提交失败即可判断未成交 | HTTP 5xx/网络超时后，订单可能已经成功 | `UNKNOWN_SUBMISSION` 状态；先按 `clientOrderId` 查询，再决定补偿 |
| 进程内 `RiskState` 足够 | 重启或 WebSocket 断线后状态丢失 | 交易所快照 + 本地事件账本 + 对账器 |
| `float` 适合下单和记账 | 十进制精度误差会造成精度拒单和账本偏差 | 数量、价格、金额、手续费使用 `Decimal` |
| `KILL_SWITCH` 拒绝一切订单 | 事故时可能阻止必要的 reduce-only 平仓 | 分离 `HALT_NEW_RISK` 与 `EMERGENCY_FLATTEN` |
| `max_total_exposure` 代表策略资金占用 | 当前代码可能按两腿名义额重复计算 | 明确定义 pair notional、gross leg notional、margin usage 三种口径 |

## 3. Binance API 约束

本节依据 Binance 官方开发者文档。官方接口、参数和限制可能变更，代码上线前必须重新核对链接和变更日志。

### 3.1 认证与签名

Spot 和 Futures 的受保护接口需要 API Key；交易接口需要 `TRADE` 权限，账户和订单查询需要 `USER_DATA` 权限，用户数据流管理需要 `USER_STREAM` 权限。API Key 默认不能交易，必须在 Binance API 管理页面显式开启交易权限。

HMAC 方案：

1. 按接口要求构造参数序列化字符串。
2. 加入 `timestamp`，并使用小于等于 60000 ms 的 `recvWindow`；初始值建议 5000 ms。
3. 使用 API Secret 对完整 payload 做 HMAC-SHA256。
4. 将十六进制签名加入请求。
5. 通过 `X-MBX-APIKEY` 发送 API Key。
6. 不记录原始 payload、Secret、完整请求 URL 或签名。

签名组件必须是独立模块，并用官方示例建立 golden tests。签名输入的参数顺序、URL 编码、query string 与 body 混合方式都必须固定并测试。

### 3.2 需要实现的接口范围

初版只实现策略必须的接口，避免把钱包、提现、杠杆产品等无关能力带进进程。

| 用途 | Spot | USDⓈ-M Futures |
|---|---|---|
| 交易规则 | `GET /api/v3/exchangeInfo` | `GET /fapi/v1/exchangeInfo` |
| 账户快照 | `GET /api/v3/account` | `GET /fapi/v3/account` 或当前官方等价接口 |
| 当前订单 | `GET /api/v3/openOrders`、`GET /api/v3/order` | `GET /fapi/v1/openOrders`、`GET /fapi/v1/order` |
| 下单 | `POST /api/v3/order` | `POST /fapi/v1/order` |
| 撤单 | `DELETE /api/v3/order` | `DELETE /fapi/v1/order` |
| 订单历史/成交 | `GET /api/v3/allOrders`、`GET /api/v3/myTrades` | `GET /fapi/v1/allOrders`、`GET /fapi/v1/userTrades` |
| 现货手续费 | `GET /sapi/v1/asset/tradeFee` 或当前官方等价接口 | 账户实际费率接口/账户页面核对 |
| Futures 持仓 | 不适用 | `GET /fapi/v3/positionRisk` 或当前官方等价接口 |
| 杠杆/保证金 | 不适用 | 上线前固定并查询 `changeInitialLeverage`、`changeMarginType` 状态 |
| 交易所熔断辅助 | 不适用 | Futures `POST /fapi/v1/countdownCancelAll`，用于订单自动过期保护 |

初版策略只允许：

- Spot：`MARKET` 或带价格保护的 `LIMIT + IOC` 买入/卖出。
- Futures：单向持仓模式 `positionSide=BOTH`；开仓卖出，平仓使用买入并带 reduce-only/close-position 语义。
- 禁止程序自动调用提现、内部转账、资产划转、动态加杠杆和跨产品借贷接口。
- 杠杆、保证金模式、持仓模式在启动预检中读取并校验，不符合预期则拒绝启动。

### 3.3 交易规则与数量归一化

不能直接把回测数量发给交易所。每个 symbol 启动前必须读取并缓存规则，至少处理：

- `PRICE_FILTER.tickSize`：价格按 tick 对齐。
- `LOT_SIZE.stepSize/minQty`：数量按 step 对齐。
- `MARKET_LOT_SIZE`：市价单可能有独立数量规则。
- `MIN_NOTIONAL` / `NOTIONAL`：检查最小和最大名义额。
- symbol `status`、合约类型、报价资产、保证金资产。
- Spot 和 Futures 的精度、最小数量、最小名义额分别处理。

数量和价格统一使用 `Decimal`，禁止用二进制浮点数直接格式化下单参数。归一化后如果名义额低于最小值、数量变为零或两腿无法在容差内匹配，订单必须在本地拒绝。

### 3.4 用户数据流

REST 适合提交和校准，WebSocket 适合低延迟接收状态。两者不能互相替代。

- Spot 用户流：处理 `executionReport`，更新订单和成交；同时关注账户余额更新。
- Futures 用户流：处理 `ORDER_TRADE_UPDATE`、`ACCOUNT_UPDATE` 和用户流过期事件。
- 用户流需要定期 keepalive；断线、过期、序列不连续或事件解析失败时立即标记状态不可信。
- 重连后不能只等待新事件，必须先 REST 拉取账户、开放订单、持仓和指定订单状态，再继续接收事件。
- WebSocket 事件必须带接收时间、交易所事件时间、连接代次和原始事件指纹，禁止记录敏感字段。

### 3.5 错误和限流

必须显式区分：

- `400` 参数/规则错误：修复或拒绝，不盲目重试。
- `401/403` 认证或权限错误：立即停机并告警。
- `408` 请求超时：对下单而言状态可能未知，进入订单查询流程。
- `429` 触发限流：尊重 `Retry-After`，全局退避，不继续发送请求。
- `418` IP 自动封禁：立即停止所有请求，等待封禁结束。
- `5xx`：订单操作结果可能未知，不能简单视为“下单失败”；按 client order id 查询。
- `409`：某些撤单替换操作可能部分成功，分别记录取消和新单结果。
- `-1021`：时钟偏移；停止交易，重新获取 server time 并检查系统 NTP。
- `-1022`：签名错误；停止交易，不能自动重复发送同一请求。
- `-2010/-2011/-2013`：订单拒绝、撤单拒绝、订单不存在；按接口上下文判断是否需要对账。

请求调度器必须是全局共享的，不能让 Spot、Futures、用户流保活各自维护独立限流计数。读响应头中的权重使用量，并在软阈值前主动降速。

## 4. 目标架构

### 4.1 分层

```text
CLI / Live Runner
       |
       +-- Strategy Signal Adapter       只产生交易意图
       |
       +-- Portfolio Coordinator         计算目标仓位和替换计划
       |
       +-- Execution Service             订单状态机、双腿编排、恢复
              |
              +-- Risk Gate               开仓/平仓/减仓权限
              +-- Spot Adapter             签名 REST + Spot user stream
              +-- Futures Adapter          签名 REST + Futures user stream
              +-- Rule Normalizer          exchangeInfo 规则
              +-- Reconciler               REST 快照与本地账本对账
              +-- State Store              SQLite 事件账本和快照
              +-- Audit / Metrics          审计、指标、告警
```

建议新增：

```text
src/cointrader/execution/
  auth.py                 HMAC、时间戳、敏感字段隔离
  transport.py            HTTP、超时、限流、重试分类
  models.py               Order、Fill、Position、PairExecution 等领域模型
  rules.py                exchangeInfo 解析和 Decimal 规则归一化
  spot.py                 Spot 私有 REST 适配器
  futures.py              Futures 私有 REST 适配器
  order_state.py          订单状态机
  pair_executor.py        双腿开仓/平仓/补偿
  reconcile.py            启动、重连、周期性对账
  store.py                SQLite 事件账本和快照
  user_stream.py          Spot/Futures 用户流管理
  metrics.py              实盘指标

src/cointrader/live/
  service.py              实盘生命周期和主循环
  portfolio.py            信号到目标仓位的转换
```

`live/` 是上层编排层，可以同时调用 `data/`、研究策略和 `execution/`。`data/`、`research/`、`backtest/` 继续禁止反向 import `execution/`，保持现有静态安全约束。

### 4.2 运行模式

将运行模式从两个布尔环境变量的组合升级为明确模式：

```text
PAPER      本地模拟，不发私有请求
TESTNET    测试网真实订单，使用测试网凭证
SHADOW     读取真实行情和账户，但只生成意图，不下单
LIVE       主网真实订单，需要额外人工确认和所有预检通过
```

默认 `PAPER`。目标配置只放模式和非敏感参数，凭证仍只能来自环境变量或外部 Secret Manager：

```yaml
execution:
  mode: paper
  recv_window_ms: 5000
  request_timeout_seconds: 5
  order_ack_timeout_seconds: 3
  max_order_retries: 0
  state_db: data/live/trading.sqlite3
  audit_path: logs/audit.log
  user_stream_keepalive_seconds: 1800
  reconciliation_interval_seconds: 30
  max_market_data_age_seconds: 5
  max_orderbook_spread_pct: 0.002
  max_leg_slippage_pct: 0.001
  max_unhedged_seconds: 10
  one_way_position_mode: true
  margin_type: isolated
  leverage: 1
```

主网启动时必须满足：

- 明确 `LIVE` 模式，而不是只把 `COINTRADER_USE_TESTNET=false`。
- 独立 live API Key；禁止提现；绑定固定出口 IP；只开必需权限。
- 交易进程所在主机和账户已人工确认。
- `KILL_SWITCH`/`HALT_NEW_RISK` 状态清晰，且完成启动对账。
- 单实例锁存在；同一账户和 symbol 禁止两个执行进程并发管理。

## 5. 领域模型与状态账本

### 5.1 核心对象

使用不可变或受控更新的领域对象，金额字段使用 `Decimal`：

- `OrderIntent`：策略想做什么，包含 `intent_id`、symbol、market、side、target_qty、reason、strategy_version、signal_time。
- `OrderRequest`：经过规则和风控归一化后的交易所请求，包含唯一 `client_order_id`、价格保护、是否 reduce-only。
- `Order`：交易所订单状态，包含 exchange order id、client order id、原始数量、累计成交量、平均成交价、状态、最后更新时间。
- `Fill`：每次实际成交，包含成交 id、成交量、成交价、手续费资产和手续费金额。
- `PairExecution`：一组 Spot/Futures 对冲操作，包含目标 pair notional、两腿实际成交、hedge ratio、补偿状态。
- `PositionSnapshot`：Spot 数量、Futures 数量、标记价、基差、保证金和时间戳。
- `AccountSnapshot`：可用余额、钱包余额、权益、未实现盈亏、保证金率、资金费累计。
- `ReconciliationResult`：本地账本与交易所快照的差异、是否允许继续开仓。

### 5.2 本地持久化

使用 SQLite，不依赖进程内内存作为唯一事实源。建议表：

- `execution_intents`
- `pair_executions`
- `orders`
- `fills`
- `position_snapshots`
- `account_snapshots`
- `exchange_events`
- `risk_decisions`
- `reconciliation_runs`
- `service_leases`

原则：

1. 先写本地 intent，再提交交易所订单。
2. 每次状态变更追加事件，并更新当前快照。
3. 交易所订单 id、client order id、fill id 建唯一索引。
4. 所有时间使用 UTC，保存交易所时间和本地接收时间。
5. 数据库不保存 API Secret；日志不保存签名和完整认证请求。
6. SQLite 文件需要定期备份，但备份仍不得包含密钥。

## 6. 双腿执行设计

### 6.1 开仓状态机

目标：现货多头 + Futures 空头，实际数量尽可能 delta-neutral。

```text
NEW_INTENT
  -> PRECHECK
  -> SUBMIT_PERP
  -> PERP_ACKNOWLEDGED
  -> PERP_PARTIAL/FILLED
  -> SUBMIT_SPOT_FOR_EXECUTED_QTY
  -> SPOT_PARTIAL/FILLED
  -> HEDGE_VERIFIED
  -> COMPLETE
```

异常状态：

```text
任何提交超时 -> UNKNOWN_SUBMISSION
UNKNOWN_SUBMISSION -> QUERY_BY_CLIENT_ORDER_ID
确认已成交 -> 继续状态机
确认未成交 -> 重新规划，不能重复盲下
部分成交 -> 只按实际成交量补另一腿
另一腿失败 -> COMPENSATE_OR_FLATTEN
无法在时限内补偿 -> HALT_NEW_RISK + CRITICAL_ALERT
```

执行规则：

1. `PRECHECK` 同时检查账户余额、保证金、symbol 规则、盘口新鲜度、价差、费率、日亏损、现有裸头寸和重复 intent。
2. 默认先提交 Futures 空头，避免先买现货后无法开合约空头。
3. Spot 数量取 Futures 实际 `executedQty`，再按 Spot 规则向下归一化。
4. 若 Spot 归一化后相差超过 hedge tolerance，不执行剩余部分；选择补偿或平掉 Futures。
5. 部分成交时禁止继续提交固定目标数量。每次补单必须基于交易所已确认的累计成交量。
6. 每个订单设置唯一 `newClientOrderId`，格式包含策略版本、pair execution id、leg、随机短后缀；长度和字符集遵守接口规则。
7. 初始版本不使用无限重试。对下单请求的重试上限为零；超时只做查询和恢复。
8. 订单成交价格必须与预提交的最大滑点保护比较，超出则停止新开仓并告警。

### 6.2 订单类型

建议分两阶段：

- Testnet 与最初 canary：允许 `MARKET`，但名义额极小，提交前必须检查盘口、价差和价格变化；成交后强制校验实际滑点。
- 稳定版本：优先使用 `LIMIT + IOC`，用价格上限/下限提供可验证的滑点边界；IOC 未完整成交时撤销剩余量并进入补偿状态。

不能用“市价单通常马上成交”代替成交保证。市价单可能受到盘口深度、网络延迟和极端波动影响。

### 6.3 平仓状态机

平仓是减风险操作，但仍必须按实际成交量管理：

```text
CLOSE_INTENT
  -> PRECHECK_CLOSE
  -> SUBMIT_SPOT_SELL / SUBMIT_PERP_REDUCE_ONLY
  -> FILL_TRACKING
  -> RESIDUAL_POSITION_CHECK
  -> COMPLETE 或 COMPENSATE_RESIDUAL
```

- 平仓请求应允许绕过开仓名义额上限，但不能绕过签名、账户一致性、symbol 规则和只减仓语义。
- Futures 平仓必须带 reduce-only 或明确的 close-position 语义，并验证不会意外反向开仓。
- 若一腿已完全平掉，另一腿残留，优先执行减少剩余风险的补偿订单。
- 若交易所不可用，立刻停止新增风险，并把人工操作所需的精确数量、方向、symbol 和订单状态写入告警。

### 6.4 对冲完成判定

不能以“两个 API 调用返回 200”判定完成。至少同时满足：

- 两腿订单最终状态已确认。
- 两腿累计成交量已记录。
- Spot 与 Futures 的可比名义额差异低于 `hedge_tolerance`。
- Futures 持仓方向和数量与预期一致。
- Spot 余额与本地持仓一致。
- 手续费、资金费和成交均价已经入账。
- 最近市场数据和账户事件没有过期。

## 7. 风控设计

### 7.1 风控层次

1. **启动风控**：模式、API 权限、时钟、账户、持仓模式、保证金模式、规则缓存、数据库和单实例锁。
2. **意图风控**：策略阈值、候选币种、目标仓位、重复意图、换仓频率。
3. **订单风控**：数量、名义额、价格保护、盘口深度、每分钟订单数。
4. **组合风控**：pair notional、总 gross exposure、单 symbol exposure、可用余额、保证金率。
5. **运行时风控**：裸腿时长、hedge ratio、基差、日亏损、WebSocket 新鲜度、对账差异。
6. **事故风控**：停止开新风险、只减仓、紧急平仓、人工接管。

### 7.2 风控口径

必须在代码和报告中分别记录：

- `pair_notional`：一组对冲仓位的一侧名义额，用于策略仓位。
- `gross_leg_notional`：现货名义额 + Futures 名义额，用于市场和执行压力。
- `margin_usage`：Futures 初始/维持保证金及可用余额占用，用于账户安全。
- `unhedged_notional`：两腿无法抵消的实际名义额，用于裸头寸告警。

默认目标：

- 主网初始杠杆 1x，最多由人工审批改为 2x；不动态加杠杆。
- 初始 canary 的单 pair notional 远低于现有 `200 USDT` 单笔上限，建议先使用能覆盖手续费和最小订单限制的最小可行值。
- `max_unhedged_seconds` 从当前 60 秒收紧到 10 秒量级；具体值以 testnet 延迟和订单深度测试结果决定。
- 日亏损同时计算已实现、未实现、手续费、资金费和未平仓估值，不只看 `realized_pnl_today`。
- 任何未确认订单、对账不一致、账户事件过期、保证金率异常都禁止新增仓位。

### 7.3 停机语义

把现有单一 `KILL_SWITCH` 拆成两个概念：

- `HALT_NEW_RISK`：拒绝开仓、换仓、增加数量；允许经过校验的取消订单和 reduce-only 平仓。
- `EMERGENCY_FLATTEN`：显式人工操作触发，尝试撤单并按当前实际持仓平仓；每个动作写审计日志，失败时升级人工告警。

删除停机文件不能自动恢复主网交易。恢复必须重新执行启动预检和对账，并要求人工确认。

## 8. 启动、重启与对账

### 8.1 启动顺序

```text
1. 加载非敏感配置
2. 读取模式，默认 PAPER
3. 加载对应凭证，不打印明文
4. 校准 server time，检查本机 NTP
5. 获取 Spot/Futures exchangeInfo
6. 获取账户余额、开放订单、Spot 资产、Futures 持仓
7. 打开 SQLite 并取得单实例 lease
8. 将交易所状态与本地账本对账
9. 检查是否有未确认订单、裸腿或未知 intent
10. 只有全部通过，才启动用户数据流
11. 用户数据流稳定后才允许策略产生开仓意图
```

### 8.2 重启和断线恢复

任何以下情况都进入 `RECOVERY`，禁止开新仓：

- 进程重启。
- Spot/Futures 用户流断线或过期。
- 事件解析失败或连接代次变化。
- REST 下单响应超时。
- 本地数据库提交失败。
- 对账发现交易所存在本地未知订单或持仓。

恢复流程：

1. 停止新意图。
2. 获取账户、开放订单、订单历史、成交、Spot 余额和 Futures 持仓。
3. 以交易所状态作为当前风险事实，和本地事件账本逐项比对。
4. 对未知订单先查询并记录，不自动重复下单。
5. 对裸头寸只执行补腿或平仓，不执行新策略仓位。
6. 对账一致、用户流新鲜、风控恢复后，才允许进入 `RUNNING`。

## 9. 密钥和部署安全

### 9.1 API Key

- Spot 和 Futures 至少使用专用交易 Key；更高安全级别可拆成交易 Key 与只读监控 Key。
- 禁止提现权限。
- 强制 IP 白名单，只允许运行节点出口 IP。
- 只启用 Spot/Futures 交易和必要的 USER_DATA/USER_STREAM 权限。
- 主网和 testnet 使用不同环境变量、不同账户、不同启动配置。
- Secret 只通过环境变量、systemd credentials、容器 secret 或外部 Secret Manager 注入，不写入 YAML、SQLite、日志、报告或 shell 脚本。
- 泄露后立即撤销 Key、触发停机、核对订单和资产，再创建新 Key。

### 9.2 主机与进程

- 实盘运行在专用 Linux 用户下，最小文件权限。
- 使用 systemd 或同等进程管理器，设置自动重启但不自动绕过 `RECOVERY`。
- 使用单实例锁，防止两个进程同时管理同一账户。
- 日志按天轮换，审计日志追加写；磁盘不足必须告警。
- 网络代理、出口 IP、系统时间和 DNS 纳入启动检查。
- 运行时不允许开发者手工修改配置文件后热加载；改配置需停新单、对账、重启。

## 10. 可观测性与告警

必须同时提供结构化日志、指标和人工可读摘要。

关键指标：

- `order_submit_total{market,side,result}`
- `order_ack_latency_seconds`
- `order_unknown_total`
- `order_reconcile_mismatch_total`
- `pair_hedge_ratio`
- `unhedged_notional`
- `unhedged_duration_seconds`
- `account_available_balance`
- `futures_margin_ratio`
- `realized_pnl_24h`、`unrealized_pnl`
- `funding_pnl`、`fee_paid`
- `basis_pct`
- `user_stream_age_seconds`
- `rest_rate_limit_used_ratio`
- `strategy_signal_count`、`order_rejection_count`

立即告警：

- 任一裸腿超过阈值。
- 订单提交结果未知。
- Spot/Futures 对账不一致。
- 保证金率接近危险线。
- 用户流过期或数据陈旧。
- HTTP 418、连续 429、认证错误、签名错误、时钟错误。
- 单日亏损触线。
- 磁盘、数据库、审计日志写入失败。

## 11. 测试计划

### 11.1 单元测试

新增测试至少包括：

- HMAC-SHA256 签名 golden vector、参数编码、`recvWindow` 和时间戳。
- Spot/Futures exchangeInfo 规则解析、tick/step 向下归一化、最小名义额。
- 订单状态机所有状态转移和非法转移拒绝。
- 重复 `clientOrderId` 不产生重复 intent。
- 408/5xx 后进入 `UNKNOWN_SUBMISSION`，查询后只允许一次明确恢复。
- 部分成交按 `executedQty` 补腿，不按原始目标数量重复下单。
- Spot 与 Futures 不同精度时 hedge ratio 和残余量计算。
- reduce-only 平仓不能反向开仓。
- 对账差异会阻止新开仓。
- `HALT_NEW_RISK` 阻止新增但允许受控减仓。
- 日亏损包含已实现、未实现、手续费和资金费。
- 日志、异常、审计记录不包含 Secret、signature、完整 API URL。

测试 HTTP 层使用 `httpx.MockTransport` 或等价 mock，不在默认测试中访问真实交易所。

### 11.2 故障注入

必须模拟：

- 提交前网络断开。
- 交易所已接单但 HTTP 响应超时。
- Spot leg 拒单。
- Futures leg 部分成交。
- WebSocket 断线、过期、重复事件、乱序事件。
- REST 与用户流先后顺序不一致。
- 本地数据库提交失败。
- 服务器重启后存在开放订单和裸头寸。
- 规则更新导致原数量不再合法。
- 429、418、5xx、-1021、-1022。

验收不是“异常被捕获”，而是：无重复订单、无无限重试、无静默裸头寸、能恢复或明确进入人工接管。

### 11.3 Testnet 集成测试

顺序固定：

1. 申请独立 testnet Key，确认没有主网权限。
2. `exchangeInfo`、server time、账户查询成功。
3. 验证持仓模式、保证金模式和杠杆。
4. 使用最小可行数量执行一组开仓双腿。
5. 验证部分成交/事件更新/实际手续费。
6. 模拟 WebSocket 断线并完成 REST 对账。
7. 执行平仓，验证最终 Spot 余额和 Futures 持仓归零。
8. 重启进程，验证数据库恢复和重复订单防护。
9. 连续运行至少 7 天 shadow/testnet，不出现未解释的对账差异。

Testnet 通过不代表主网通过。Testnet 的流动性、延迟、撮合和故障特征不能完全代表主网。

## 12. 分阶段实施计划

### M0：策略与资金边界

交付：

- 最新回测、悲观成本、基差压力、交易所全损情景报告。
- 明确可承受最大损失、初始 canary 名义额和停止条件。
- 确认实际 Spot/Futures 手续费和资金费记账口径。

门槛：策略不满足项目既定收益/风险标准时，停止实盘开发，不以加杠杆或放宽风控补救。

### M1：认证与只读私有 API

交付：

- `auth.py`、`transport.py`。
- server time、账户、订单查询、规则查询。
- 完整脱敏和错误分类。

门槛：无真实下单；所有签名测试通过；错误和限流测试通过。

### M2：订单适配和状态账本

交付：

- Spot/Futures adapter。
- `Decimal` 规则归一化。
- SQLite 事件账本。
- client order id 和 `UNKNOWN_SUBMISSION` 恢复流程。

门槛：mock 故障注入通过；不允许用浮点直接发单。

### M3：双腿执行和对账器

交付：

- Pair execution 状态机。
- 用户数据流、keepalive、断线恢复。
- 启动/周期/重连对账。
- 新增风险停止与减仓路径分离。

门槛：可证明部分成交、超时、重启均不会重复开仓或静默形成裸腿。

### M4：Testnet 端到端

交付：

- 真实 testnet 开仓、部分成交处理、平仓、重启恢复报告。
- 延迟、滑点、订单拒绝、用户流稳定性报告。

门槛：至少连续 7 天无未解释对账差异；所有严重告警都能触发并处理。

### M5：Shadow/Paper 长跑

交付：

- 实时信号、预期订单、实际盘口和假设成交的对账报告。
- 预测成本与真实可成交成本比较。
- 运行手册、事故演练记录。

门槛：至少 14 天；不出现重复 intent、错误数量、过期数据下单决策或未记录状态。

### M6：主网 canary

交付：

- 独立主网 API Key 和 IP 白名单。
- 人工签字式启动清单。
- 最小可行名义额的一组 pair，禁止自动放量。
- 每次开仓和每次平仓人工复核告警。

门槛：先完成若干次开平仓闭环，再连续运行观察；任何未知订单、裸腿、对账差异、认证/时钟/限流错误都自动停止新风险。

### M7：受控放量

只有满足以下条件才可提高限额：

- canary 运行期内无严重事故。
- 真实成交滑点、手续费、资金费与模型差异在预设范围。
- 账户、订单、持仓对账持续一致。
- 风控和人工事故演练完成。
- 每次只提高一个限额，并保留可回滚配置和变更记录。

## 14. 不做的事情

初版明确不做：

- 不做多交易所路由。
- 不做提现、自动转账、自动补充保证金。
- 不做动态加杠杆、自动借贷、自动切换保证金模式。
- 不做无限重试和“下单失败后再发一遍”的简单逻辑。
- 不做只依赖轮询、只依赖 WebSocket 或只依赖本地状态的执行系统。
- 不把 testnet 的成功当作主网安全证明。
- 不在策略亏损时自动放宽阈值、提高杠杆或关闭停机机制。

## 16. 最终验收标准

实盘开发完成的定义不是“能发出一笔订单”，而是：

> 在订单部分成交、响应超时、WebSocket 断线、进程重启、规则变化、限流和交易所错误发生时，系统都能避免重复下单，准确知道实际持仓；不能自动恢复时，能停止新增风险并给出可执行的人工接管信息。

只有 M0-M6 全部通过，且主网 canary 完成真实开平仓闭环后，才允许讨论放量。
