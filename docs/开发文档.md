# CoinTrader 开发文档

> 本文用于指导低级模型和开发者完成 `docs/任务规划.md` 中的开发工作。
> 本文是实施手册，不是策略说明，也不是授权真实交易的文件。
>
> 任何实现都必须先阅读本文和 `docs/任务规划.md`。如果代码、本文、任务规划冲突，以以下优先级处理：
>
> 1. 安全约束和交易所实际状态；
> 2. `docs/任务规划.md` 的验收标准；
> 3. 本文的实现步骤；
> 4. 现有代码的兼容性。
>
> 任务规划没有要求的功能不要顺手增加。不要为了产生更多交易而降低策略门槛、提高杠杆、关闭对账或绕过异常。

## 1. 开发目标

最终目标是在 Binance Demo Trading 固定环境中完成一次可审计的 7 天试运行闭环：

```text
历史/实时资金费数据
    -> 实时策略候选评估
    -> 可解释的 signal_decision
    -> 唯一交易 intent
    -> Spot + Futures 双腿执行
    -> 订单和成交事件
    -> 账户/持仓对账
    -> funding、fee、basis、realized/unrealized PnL
    -> 只读查询
    -> 完整 AI 报告数据包
```

必须达到以下性质：

- 策略真实使用入场、退出、连续正费率、流动性和换仓规则。
- 每个候选币种都有通过或拒绝理由。
- 每笔开仓和平仓都能从 `signal_decision` 追到 intent、pair、order、fill、费用、资金费、对账和 PnL。
- 进程重启、用户流失效、订单响应超时、部分成交、数据库重启后不会重复下单。
- 状态未知时停止新增风险；不能自动解决时进入 `RECOVERY` 或 `HALTED`，并给出人工处理信息。
- 查询命令只读，不触发下单、撤单、杠杆变更或配置写入。
- 报告只基于账本和快照，不从普通日志猜收益。
- 完成工作包一、二和演练前，不得开始正式 7 天计时。

7 天试运行不能证明策略长期盈利，也不能证明主网安全。报告必须明确 Demo、poll 用户流和样本长度的限制。

## 3. 当前实现状态和明确缺口

### 3.1 已有能力

当前已有以下基础，优先复用，不要重新发明：

- `data/`：公开数据 API、资金费历史、K 线、缓存和限流。
- `research/scanner.py`：资金费候选扫描、周期年化、连续正费率、流动性筛选。
- `execution/auth.py`、`transport.py`：签名 REST 和错误/限流处理。
- `execution/rules.py`：交易规则和 `Decimal` 归一化。
- `execution/order_state.py`：订单状态转移。
- `execution/pair_executor.py`：双腿开仓、平仓、部分成交和补偿骨架。
- `execution/reconcile.py`：启动/周期对账骨架。
- `execution/user_stream.py`：WebSocket 或 REST poll 用户流。
- `execution/store.py`：SQLite 账本、订单/成交/快照/对账和单实例锁。
- `live/service.py`：启动预检、服务状态、用户流新鲜度、周期对账和开仓循环。
- `live/portfolio.py`：报价新鲜度、基差和 canary 名义额检查。
- 安全静态测试和默认拒绝闸门。

### 3.2 必须修复的缺口

当前实现不能直接称为“策略已接入实盘”。必须处理：

1. `build_live_context()` 没有注入真实 `signal_provider`，默认 provider 返回空列表。
2. `LiveService._default_risk_state()` 的 `total_capital=0`，真实开仓会被拒绝；必须从真实账户快照构建资金状态，字段缺失时拒绝开仓。
3. `FundingScanner` 是低频全市场研究扫描器，不能直接放在 5 秒主循环中。
4. `LiveService.run_once()` 目前只处理开仓，不处理策略退出、最长持仓和换仓。
5. `active_pair_for_symbol()` 只检查未终态 pair；一个已完成开仓仍可能有实际持仓，不能只依赖 pair 终态防重复。
6. `StateStore` 缺少运行会话、策略决策、资金费现金流、完整关联字段和迁移版本。
7. 当前已有 fills、账户快照、持仓快照，但没有统一 live PnL 聚合器。
8. CLI 目前只有 `live doctor` 和 `live run`，没有稳定的 `status/positions/orders/trades/pnl/report` 查询出口。
9. 启动预检只使用 `report.symbols[0]` 检查杠杆/保证金，不符合“所有允许交易 symbol 逐个检查”的要求。
10. Demo 只能使用 `execution.user_stream_mode=poll`。任何文档、日志和报告都不能把 poll 描述成主网 WS 等价能力。

## 4. 不可违反的开发规则

### 4.1 安全规则

- 不在代码、测试、配置、文档示例中写真实 API Key 或 Secret。
- 不把 Secret、签名、完整认证 URL、完整认证 payload 写入日志、SQLite 或报告。
- 不实现提现、转账、自动补保证金、自动借贷或动态加杠杆。
- Demo 运行固定 `1x`、`isolated`、`positionSide=BOTH`，除非任务规划明确改变。
- 不把 `COINTRADER_TRADING_ENABLED`、`KILL_SWITCH`、`--confirm-live` 绕过或弱化。
- `HALT_NEW_RISK`/现有停机逻辑必须阻止新增风险，但允许经过校验的 reduce-only 平仓路径。
- 不把异常改成“忽略并继续”。未知订单、未知成交、裸腿、账本写失败和对账失败必须阻止新开仓。
- 不自动重试真实下单。提交超时或 5xx 后只能按 `clientOrderId` 查询和恢复，不能盲目再发一单。

### 4.2 数据和精度规则

- 交易数量、价格、金额、手续费、资金费使用 `Decimal`；数据库使用文本保存 Decimal。
- 所有时间保存 UTC 毫秒；同时区分交易所时间和本地接收时间。
- 交易所唯一 id、client order id、fill id、事件 fingerprint 必须幂等。
- Schema 变化必须通过迁移或版本处理。不能让用户删除 SQLite 重新建库来“解决”升级问题。
- 查询默认只读，不能通过查询代码调用交易写接口。
- 原始 payload 只保存必要的非敏感字段，并在写入前脱敏。

### 4.3 架构依赖规则

依赖方向保持：

```text
data / research / backtest  -> 不得 import execution
live                        -> 可以调用 data、research、execution
execution                   -> 不依赖 live 的策略协调器
CLI                         -> 负责装配和查询入口，不承载策略算法
```

策略判断放在 `live/` 或 `research/` 的协调层，不放进 `execution/`。执行层只负责把已经确认的交易意图安全执行，并记录事实。

## 5. 目标模块边界

推荐目标结构如下。已有文件优先扩展；只有职责确实独立时才新建文件。

```text
src/cointrader/
  live/
    service.py              生命周期、状态转换、主循环
    portfolio.py            Signal 和报价保护
    strategy.py             实时策略协调器、候选和退出判断
    decisions.py            signal_decision/exit_decision 领域对象
    account_state.py        交易所快照到 RiskState 的转换
    snapshots.py            周期快照采样

  execution/
    models.py               Order、Fill、PairExecution、Snapshot 等纯模型
    store.py                SQLite 账本和查询
    migrations.py            Schema 版本迁移（如采用独立迁移模块）
    pair_executor.py        双腿开平仓和补偿
    reconcile.py            交易所事实与本地账本对账
    risk.py/risk_gate.py    风控判定和停止新风险
    ...

  reporting/
    pnl.py                  基于账本的 PnL 聚合
    export.py               JSON/CSV/JSONL/manifest 导出
```

如果不新建 `reporting/`，可以把等价职责放在 `live/` 或 `execution/`，但必须保持“计算 PnL”和“交易执行”分离。不要为了少建文件把所有逻辑塞进 `service.py` 或 `cli.py`。

## 6. 领域对象和关联链路

### 6.1 统一关联链

一笔策略交易必须能按以下链路反查：

```text
run_session
  -> signal_decision
  -> pair_execution
  -> execution_intent
  -> order
  -> fill
  -> funding_cashflow / account_snapshot / position_snapshot
  -> reconciliation_run
  -> pnl_ledger
```

任何新建记录都要尽量带上：

- `run_id`；
- `symbol`；
- `pair_execution_id`；
- `intent_id`；
- `strategy_version`；
- `created_ms` 或交易所时间；
- `source` 和 `reason`。

### 6.2 实时策略输入

策略协调器每次评估一个候选 symbol 时，输入至少包括：

```text
symbol
funding_interval_hours
recent_funding_rates
recent_funding_timestamps
entry_lookback_periods
exit_lookback_periods
trailing_annualized
exit_average_annualized
consecutive_positive_periods
quote_volume_3d_avg
liquidity_tier
spot_price/perp_price
quote_ts_ms
current_position
position_age_periods
active_intent/order/pair 状态
available_capital
current_position_count
```

实时行情必须重新拉取或读取新鲜缓存。候选池可以低频刷新，但提交开仓前必须重新获取新鲜 Spot/Futures 报价和时间戳。

### 6.3 策略决策输出

每个候选都必须输出一个可持久化的决策对象，至少包括：

```text
symbol
run_id
ts_ms
decision_kind: OPEN / HOLD / EXIT / REPLACE / SKIP
allowed: true/false
reason_code
reason_text
strategy_version
config_hash
funding metrics snapshot
liquidity metrics snapshot
position state snapshot
quote timestamp
requested_notional
```

拒绝也必须落盘。示例 `reason_code`：

```text
INSUFFICIENT_HISTORY
TRAILING_RATE_BELOW_THRESHOLD
CONSECUTIVE_POSITIVE_TOO_SHORT
LOW_LIQUIDITY
EXCLUDED_ASSET
MAX_POSITIONS
ALREADY_HELD
ACTIVE_INTENT
ACTIVE_ORDER
STALE_QUOTE
ACCOUNT_STATE_UNKNOWN
RECONCILIATION_BLOCKED
```

不要只在日志打印“跳过 BTCUSDT”。必须能在数据库中知道跳过原因和判断输入。

## 7. 工作包一：实时策略交易流程

工作包一完成后，系统必须能在不降低策略门槛的前提下，完成策略开仓、持仓期间去重、策略退出和受控平仓。

### 7.1 实时策略协调器

新增实时协调器，不能直接复用 `FundingScanner.scan()` 作为 5 秒 provider。

建议拆成两个频率：

```text
低频刷新：候选 symbol、funding history、结算周期、历史成交量、策略指标缓存
主循环：读取缓存 + 获取新鲜报价 + 评估决策 + 生成 intent
```

低频刷新周期可配置，例如 1 个资金费周期或数分钟，但不能在每轮对所有 symbol 重新拉完整历史。刷新失败时保留旧缓存，但要标记数据年龄；超过允许年龄必须拒绝开仓。

实现步骤：

1. 从 `FundingScanner` 复用资金费年化、周期和流动性计算，不复制公式。
2. 为每个候选建立缓存对象，保存数据时间、指标结果和拒绝原因。
3. 以配置中的以下字段作为唯一门槛来源：
   - `strategy.entry.lookback_periods`；
   - `strategy.entry.min_trailing_annualized`；
   - `strategy.entry.min_annualized_rate`；
   - `strategy.entry.min_consecutive_positive`；
   - `strategy.selection.min_quote_volume_3d_avg`；
   - `strategy.selection.exclude_bases`；
   - `strategy.selection.max_positions`；
   - `strategy.selection.per_position_weight`。
4. 入场信号必须保存当时的指标快照，而不是只保存一个文本 `reason`。
5. 信号通过策略条件后，再调用 `build_signal()` 做价格、基差、报价新鲜度和 canary 检查。
6. `build_signal()` 不能承担资金费策略判断；它只负责交易意图前的市场数据和名义额检查。
7. 候选池分两种模式（`execution.live_symbols`）：
   - **固定模式**（非空列表）：初期只开放一个高流动性 USDT symbol，完成单 pair 闭环后再手工扩大。
   - **动态模式**（空列表，当前默认）：回测同口径 —— 全部可交易 USDT 永续（排除 `exclude_bases`）
     → 24h 成交额 >= `min_quote_volume_3d_avg` → 按量取 top `candidate_pool_max_symbols`。
     池每 `universe_refresh_seconds` 刷新一次（失败保留旧池）；候选指标按**各币自己的
     资金费结算周期**刷新（两次结算间费率不变），且每 60s 窗口限量
     `candidate_refetch_per_minute` 个 symbol 以摊平结算边界的突发请求（API 按分钟限流）；
     报价只为通过前置检查的候选
     按需获取（`PENDING_QUOTE` 中间态 → `complete_open` 定案，中间态不落账本）；
     杠杆/保证金在 symbol 首次开仓时按需验证。动态池不是「全市场自动交易」：
     每笔开仓仍受 `max_positions` / 门槛 / 风控闸门全部约束。

建议接口：

```python
class LiveStrategy:
    def refresh_candidates(self) -> None: ...
    def evaluate(self, context: LiveContext) -> list[StrategyDecision]: ...
    def complete_open(self, symbol: str, context: LiveContext,
                      quote: Quote | None) -> StrategyDecision: ...
```

`evaluate()` 必须是可测试的。网络请求应由外部数据 provider 注入，单元测试使用 fixture，不访问真实交易所。

### 7.2 开仓判断顺序

开仓判断按以下顺序执行，尽早拒绝并记录原因：

```text
1. 服务状态必须是 RUNNING
2. 用户流/轮询状态必须新鲜
3. 最近对账必须通过
4. 账户快照必须成功且字段完整
5. symbol 不在排除列表
6. funding 历史窗口完整
7. 最近 lookback 期平均年化达到阈值
8. 最近连续正费率期数达到阈值
9. 流动性达到阈值
10. 当前没有实际持仓
11. 当前没有未终态 pair/order/intent
12. 当前未超过 max_positions
13. 报价新鲜且 Spot/Futures 都可交易
14. 目标名义额在 canary、单笔、单币、总敞口内
15. 写入 signal_decision 和唯一 intent
16. 调用 PairExecutor.open_pair()
```

“没有实际持仓”必须使用交易所对账后的真实持仓或可信快照判断，不能只查询 `active_pair_for_symbol()`。

“本轮已提交”必须有进程内集合或数据库状态保护。主循环重复执行同一个 signal 时，第二次必须只产生 `SKIP` 决策，不得创建新的 intent。

### 7.3 去重要求

以下任一条件成立，都禁止重复开仓：

- 交易所存在 Spot 余额或 Futures 持仓；
- 本地存在同 symbol 的非终态开仓 pair；
- 本地存在同 symbol 的未终态 intent/order；
- 当前 run 已提交相同 symbol 的开仓；
- 对账不一致或账户状态过期；
- 正在执行平仓或换仓。

建议新增一个统一方法，例如：

```python
can_open(symbol, run_id, exchange_position, store_state) -> Decision
```

不要在 `service.py`、`pair_executor.py`、`store.py` 各自实现一套互相矛盾的重复判断。底层执行器仍必须再次检查，不能只信上层。

### 7.4 退出和换仓

把回测语义转换成实时 `ExitDecision`。判断顺序建议如下：

```text
1. 裸腿、异常、账户风险、对账差异、人工停机 -> REDUCE / FLATTEN
2. 最近 exit_lookback_periods 期平均资金费率转负 -> EXIT
3. 持仓年龄达到 max_holding_periods -> EXIT
4. 满足 replacement premium 和持仓年龄 -> REPLACE
5. 否则 HOLD
```

退出条件：

- 负资金费退出使用 `strategy.exit.exit_lookback_periods` 的最近平均值，不要误用入场窗口。
- 最大持仓使用资金费结算期数，不要直接把小时、天数和期数混用。
- 换仓必须先平旧仓并确认对账，再决定是否开新仓；不能在旧仓仍存在时叠加新仓。
- 所有退出决策先写 `signal_decisions` 或等价表，再调用 `PairExecutor.close_pair()`。
- 平仓必须使用真实 Spot 数量和 Futures 数量，Futures 使用 reduce-only 或等价只减仓语义。
- 平仓后再次调用对账，确认两腿归零；残量进入 `RECOVERY/HALTED`，不能悄悄标记成功。

7 天结束时，即使没有自然退出信号，也可以执行人工确认的统一平仓。该记录必须使用 `manual_trial_flatten`，不能伪装成自动策略退出或策略收益。

### 7.5 真实 RiskState

新增账户状态适配器，从 Spot/Futures 账户快照构建 `RiskState`。至少提供：

```text
total_capital
available_balance
wallet_balance
futures_wallet_balance
realized_pnl
unrealized_pnl
positions
unhedged_notional
margin_ratio
snapshot_ts_ms
source
```

要求：

- 账户字段缺失、查询失败、时间过期、余额为 0 或无法区分平台发放资产时，不得使用默认值放行开仓。
- `total_capital=0` 只能表示资金未知并拒绝开仓，不能表示账户真的可交易。
- 所有数量和金额在进入风控前使用 `Decimal`，若旧风控接口使用 float，转换必须集中在边界处并保留原 Decimal 快照。
- 账户快照失败应产生 `risk_decision` 和告警。
- PnL、手续费、资金费不能只通过余额差额推导；余额差额只能作为交叉验证。

### 7.6 启动预检修正

修改 `LiveService.startup()`：

- 遍历所有允许交易的目标 symbol，逐个加载 Spot/Futures 规则。
- 对每个 symbol 检查状态、最小名义额、数量精度和可交易性。
- 对每个 symbol 检查或显式设置杠杆、保证金模式和 `positionSide=BOTH`。
- 如果 Demo 无法读取杠杆，必须记录“读取不可用，已显式设置并采用”，不能写成“读取验证成功”。
- 把每个 symbol 的预检结果写入 `StartupReport.extra` 或持久化表。
- 只要任一实际候选预检失败，禁止开始正式运行；不要只检查排序后的第一个 symbol。

### 8.2 迁移要求

不要用“启动时 `CREATE TABLE IF NOT EXISTS` + 新字段直接假设存在”替代迁移。

迁移流程：

```text
打开数据库
  -> 读取 schema_version
  -> 按顺序执行未完成迁移
  -> 每个迁移在事务中完成
  -> 更新 schema_version
  -> 失败则拒绝启动，不继续交易
```

迁移测试至少覆盖：

- 空数据库从 0 升到最新版本；
- 现有项目数据库从旧版本升级；
- 升级后已有 orders/fills/pairs 查询结果不丢；
- 迁移中断后再次启动可以继续或明确失败；
- 数据库备份文件可以只读导出。

### 8.3 幂等规则

以下事件重复到达时，第二次必须不重复计入：

- 相同 `intent_id`；
- 相同 `(market, client_order_id)`；
- 相同 `(market, exchange_order_id)`；
- 相同 `(market, exchange_trade_id)`；
- 相同 `event_fingerprint`；
- 相同资金费结算事件；
- 相同对账快照不应重复制造 PnL。

数据库唯一约束是最后一道保护，业务代码也要在重复时返回“已存在/未新增”，不能把唯一约束异常当成系统崩溃。

### 8.4 PnL 口径

实现独立的账本聚合器。按 pair、run 和时间范围输出：

```text
funding_pnl
trading_fee
basis_pnl
realized_pnl
unrealized_pnl
net_pnl
cash_delta
```

建议计算顺序：

1. 从 `fills` 汇总两腿实际成交数量、成交价、手续费。
2. 从 `funding_cashflows` 汇总已确认资金费收入/支出。
3. 从开平仓成交和价格计算基差相关收益，记录公式和输入。
4. 已完成 pair 计算 realized PnL。
5. 未完成 pair 根据最新可信 Spot/Futures 价格计算 unrealized PnL。
6. `net_pnl` 使用固定公式，并在输出中写明公式版本。
7. 从账户快照计算 cash delta，作为交叉核对，不直接替代策略 PnL。

必须明确正负号。建议采用：

```text
funding_pnl = 实际收到的资金费 - 实际支付的资金费
trading_fee = -所有交易手续费的价值
basis_pnl = 两腿实际进出场价格造成的净基差收益
realized_pnl = 已平仓的 funding + fee + basis 等已确认项目
unrealized_pnl = 当前未平仓两腿按最新可信价格估值
net_pnl = 已确认策略收益 + 未实现收益
```

具体公式应以代码和 fixture 为准，但不能在不同模块使用不同口径。每个 PnL 数字必须带：

```text
source
period_start/period_end
calculation_version
reconciled
last_updated
```

禁止把以下内容自动计为策略收益：

- Demo 平台发放的 USDC 或其他资产；
- 账户权益变化中无法对应成交/资金费的部分；
- 未平仓浮盈浮亏当作已实现收益；
- 日志里的“对账通过”；
- 报告生成时间之后的数据。

如果账本 PnL 和账户快照无法解释地不一致，输出差异，不得强行修正成盈利。

### 8.5 周期采样

至少实现：

- 每次提交订单、订单状态变化、成交事件立即写账本；
- 至少每 30 秒写 Spot/Futures 账户快照和策略持仓快照；
- 每次对账写 `reconciliation_runs`；
- 资金费结算窗口后拉取实际资金费并写 `funding_cashflows`；
- 用户流事件写 `exchange_events`，poll 模式也记录来源和接收时间；
- 数据库写入失败使服务进入 `RECOVERY/HALTED`，不能仅记录 warning 后继续交易。

## 12. 低级模型常见错误

### 错误一：直接把 `FundingScanner` 放进主循环

原因：每 5 秒全市场扫描会触发限流、延迟和数据重复。正确做法是低频刷新缓存，主循环使用缓存并获取新鲜报价。

### 错误二：看到 `build_signal()` 就认为策略已完成

`build_signal()` 只检查报价、名义额、基差和 symbol；它不检查资金费率阈值、连续正费率、流动性和持仓年龄。

### 错误三：只用 `active_pair_for_symbol()` 去重

已完成 pair 仍可能代表当前真实持仓。必须同时检查交易所持仓、本地 fills、未终态 intent/order 和当前 run intent。

### 错误四：用 `total_capital=0` 的默认 RiskState 继续交易

资金未知必须拒绝开仓。不能把默认值改成一个固定资金数，也不能在异常时使用 `initial_capital` 冒充账户资金。

### 错误五：把账户余额变化当作策略 PnL

Demo 发放资金、资金划转、未实现 PnL 和策略成交收益必须分开。账户现金变化只能作为交叉检查。

### 错误六：订单请求返回异常就再次下单

超时和 5xx 可能已经成交。必须用同一个 `clientOrderId` 查询，并按查询结果恢复；不确定就停止新风险。

### 错误七：部分成交仍按原目标数量补腿

Spot 数量必须基于 Futures 实际 `executedQty`；后续补偿必须基于实际剩余量。不能按原始目标重复下单。

### 错误八：把日志文本当报告源

报告必须从 SQLite 账本、快照和导出表生成。日志只能作为辅助审计材料。

### 错误九：查询命令复用会修改交易状态的代码

`status/positions/pnl/report` 只能读，不得创建 intent、刷新杠杆、撤单、写配置或触发交易 API。

### 错误十：为测试方便关闭安全闸门

使用 fake adapter、mock transport、临时数据库解决测试问题。不要修改生产闸门让测试通过。

## 14. 完成定义

### 工作包一完成

- 实时策略和回测语义一致；
- 候选通过/拒绝原因可查询；
- 真实账户状态进入风控；
- 开仓、退出、换仓、去重和重启恢复通过测试；
- 所有 symbol 的启动预检通过；
- 没有未知资金、未知持仓和静默裸腿。

### 工作包二完成

- 数据库可迁移、可恢复、幂等；
- 每笔交易完整可追溯；
- PnL 分项有固定口径和来源；
- 查询命令只读且输出稳定；
- 报告数据包完整、脱敏、可校验；
- 数据包可直接供 AI 生成事实报告。

### 工作包三完成

- shadow 和最小 Demo 开平仓演练通过；
- 重启、停机、部分成交、超时、拒单、查询失败和数据库故障演练通过；
- 备份恢复通过；
- 连续 7 天运行符合所有验收门槛；
- 最终报告明确说明什么已证明、什么未证明。

只有三项全部满足，才可以说“完成 7 天 Demo 试运行开发”。不能把“程序启动了”“有一笔成交”或“日志显示对账通过”当作完成。

## 15. 推荐交付命令

以下命令表示目标用法。命令真正实现前不得当作已有能力使用：

```bash
# 开发验证
uv run pytest
uv run ruff check src tests
uv run mypy src/cointrader

# 正式演练前
uv run cointrader live doctor
uv run cointrader live status --json

# shadow / Demo 运行
uv run cointrader live run

# 运行中只读查看
uv run cointrader live status
uv run cointrader live positions
uv run cointrader live orders --since 24h
uv run cointrader live trades --since 7d
uv run cointrader live pnl --since RUN_START

# 结束后导出
uv run cointrader live report --run-id <run_id> --output reports/live/<run_id>
```

## 16. 最终原则

- 策略没有信号时保持没有交易，不制造样本。
- 账本不知道的事实，不得写进报告结论。
- 状态不确定时停止新增风险。
- 不能自动恢复时，提供精确的人工处理信息。
- Demo 成功不等于主网安全。
- 7 天收益不等于长期策略能力。
- 任何代码实现都必须让事实、决策、订单、成交、对账和收益可以互相追溯。
