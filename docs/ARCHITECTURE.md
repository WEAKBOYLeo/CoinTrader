# CoinTrader 架构设计

## 0. 这个项目要回答的问题

**资金费率套利（funding rate carry）在扣除真实成本后，是否还有净收益？**

在回答这个问题之前，不写任何执行层代码。整套框架的存在意义是**证伪**，不是**确认**。
如果回测跑出来收益微薄，正确的结论是"这个策略不值得做"，而不是"参数没调好"。

## 1. 分层架构

```
┌─────────────────────────────────────────────────────────┐
│ CLI (cointrader/cli.py)                                 │
└────────────┬────────────────────────────────────────────┘
             │
   ┌─────────┴──────────┬───────────────┬─────────────────┐
   ▼                    ▼               ▼                 ▼
┌──────────┐   ┌──────────────┐  ┌────────────┐  ┌──────────────┐
│  data    │   │  research    │  │  backtest  │  │  execution   │
│  数据层  │──▶│  信号层      │─▶│  回测层    │─▶│  执行层      │
│          │   │              │  │            │  │ (默认禁用)   │
└──────────┘   └──────────────┘  └────────────┘  └──────────────┘
  只读公开API      纯函数，无IO      无网络，确定性     需显式开关
```

**依赖方向严格单向**：上层可以 import 下层，下层**永不** import 上层。

| 层 | 允许 | 禁止 |
|---|---|---|
| `data/` | HTTP 读公开接口、写磁盘缓存 | 任何下单、任何签名请求 |
| `research/` | 纯计算、读缓存 | 网络 IO、文件写入 |
| `backtest/` | 读缓存、算指标 | 网络 IO、真实下单 |
| `execution/` | 下单（**默认关闭**） | 被其他层 import |

`execution` 层被 import 时本身不产生副作用，但任何真实下单路径都被
`guard.py` 的闸门拦截，见 §4。

## 2. 策略的数学定义

### 2.1 头寸结构

资金费套利 = **现货多头 + 永续空头**，等名义额。

```
t0:  买入现货 Q 个 @ spot_price     → 支出 Q * spot_price
    卖出永续 Q 个 @ perp_price     → 保证金占用 Q * perp_price / leverage
                                     另需维持保证金缓冲

持有期间:  每 funding_interval 结算一次
          收取 funding = Q * mark_price * funding_rate    (费率为正时收)
          现货与永续的价差波动 → 见 §2.3

t1:  卖出现货 + 平掉永续 → 回收本金 ± 基差损益 - 交易成本
```

### 2.2 收益分解（这是整个项目的核心公式）

```
净收益 = Σ(资金费收入)          ← 主要收益来源，可为负
        - 4条腿的交易成本        ← 见 §2.4
        - 基差收敛/扩大损益      ← 建仓时已锁定，持有中漂移，见 §2.3
        - 资金占用成本           ← 机会成本，用无风险利率做基准
```

**年化口径必须统一**：由于结算周期不统一（4h/8h/1h 三种，已实测确认），
年化公式必须按**每个币自己的周期**折算：

```
年化 = funding_rate * (24 / funding_interval_hours) * 365
```

用 8h 公式套 4h 的币，会把年化**低估一半**。`data/funding.py` 负责
从 `/fapi/v1/fundingInfo` 拉取真实周期并缓存，禁止硬编码 8。

### 2.3 基差风险（最容易被忽略的一块）

现货价 S 与永续标记价 M 不相等，基差 `b = (M - S) / S`。

- **建仓瞬间**：若 b > 0（永续溢价，牛市常态），你卖出偏贵的永续，
  相当于**建仓即赚一笔基差**；反之 b < 0 则建仓即亏
- **持有期间**：b 漂移。空永续的盈亏按 M 结算，多现货的盈亏按 S 结算，
  两者的差就是基差损益。**这是真实风险，不是零**
- **平仓瞬间**：再结算一次基差

实证上，主流币基差长期在 ±0.1% 内波动，但**极端行情下（如 2021-05、2022-11）
可以扩张到 1%+**。回测必须报告"基差最大不利变动"这个指标，
而不是假定基差恒为零。

**模型选择**：本项目默认用 `baseline` 模型（假定建仓/平仓时刻基差已按
实际历史数据结算），并提供 `zero_basis` 悲观模型（假定每次调仓白送
`max_basis_adverse` 的损失）。两个模型都跑，取悲观者的结论。

### 2.4 成本模型（全项目最需要严谨的地方）

一次完整的"进场→持有→出场"共 **4 条腿**（买现货、卖永续、卖现货、平永续）。

| 项目 | 默认值 | 说明 |
|---|---|---|
| 现货 taker 费率 | 0.100% | VIP0 无 BNB 抵扣 |
| 现货 maker 费率 | 0.100% | VIP0 |
| 现货 taker（BNB抵扣） | 0.075% | 25% 折扣 |
| 永续 taker 费率（BNB 支付） | 0.045% | 0.050% × 90% |
| 永续 maker 费率（BNB 支付） | 0.018% | 0.020% × 90% |
| 滑点（主流币） | 0.010% | 单边 |
| 滑点（小市值币） | 0.050% | 单边，流动性差 |

**全部可在 config.yaml 覆盖**，且必须能被一键改成"最悲观"配置。

往返成本（taker，BNB 抵扣，主流币）：

```
买现货 0.075% + 卖永续 0.045% + 卖现货 0.075% + 平永续 0.045%
+ 4 × 0.010% 滑点
= 0.28%
```

**这个数字是整个项目最重要的基准线**。任何策略若历史平均年化扣费后
不到它的若干倍，就不值得投入工程和资金。

> ⚠️ 上述费率为写代码时的公开标准 VIP0 费率。**上线前必须用
> `GET /sapi/v1/asset/tradeFee`（现货）与账户实际返佣页面核对**，
> 并在 config 中更新。费率算错 0.02%，一年就是 7% 的收益差。

## 3. 数据层设计

### 3.1 只读原则

`data/binance.py` **只实现公开 GET 接口**。这个类里不存在 API Key 参数，
不存在签名方法。要下单必须换用 `execution/` 下的类。
这样做的目的是让"误下单"在类型层面就不可能发生。

### 3.2 限流（实测数据）

| 接口 | 限制 | 获取方式 |
|---|---|---|
| 期货 `REQUEST_WEIGHT` | 2400 / 分钟 | 响应头 `x-mbx-used-weight-1m` |
| 期货 `ORDERS` | 1200 / 分钟，300 / 10秒 | — |
| 现货权重 | 6000 / 分钟（IP） | 响应头 `x-mbx-used-weight-1m` |

客户端必须：
1. **每个响应后读 `x-mbx-used-weight-1m` 并记录**，而不是自己估算
2. 权重超 80% 时主动 sleep（保守阈值，给并发留余量）
3. 收到 **HTTP 429** → 指数退避 + 尊重 `Retry-After` 头
4. 收到 **HTTP 418**（IP 被临时封禁）→ **立即停止所有请求**，长退避，并记录日志。
   418 意味着已经违反限流，继续请求会延长封禁
5. 收到 **5xx** → 指数退避重试，最多 5 次

### 3.3 缓存策略

- 历史数据**不可变**：资金费历史、已收盘 K 线 → 永久缓存
- 实时快照**易变**：premiumIndex、盘口 → 带 TTL 的短期缓存（默认 5s）
- 所有缓存写入使用**原子写**（写临时文件 → `os.replace`），防止进程中断留下半个文件
- 缓存文件名包含参数哈希，避免不同参数互相覆盖

## 4. 安全设计（本项目的重点要求）

### 4.1 三层隔离

**第一层：类型隔离。** 数据层客户端无签名能力（§3.1）。

**第二层：运行时闸门。** `execution/guard.py` 是唯一的真实下单入口。
任何下单调用必须同时满足：

```python
TRADING_ENABLED = env "COINTRADER_TRADING_ENABLED" == "YES_I_AM_SURE"   # ①
is_testnet      = True                                                   # ②
not kill_switch_engaged()                                                # ③（见下）
amount <= max_notional_per_order                                         # ④
total_exposure <= max_total_exposure                                     # ⑤
```

- ① 必须**精确等于**那个字符串，写 `1`/`true`/`yes` 都不行。这是故意的摩擦
- ② 默认永远走 testnet。真实盘需要**同时**改 ① 和一个独立配置项
- ③ **kill switch**：存在 `KILL_SWITCH` 文件时（默认 `./KILL_SWITCH`）
  一切下单被拒绝。这个检查是文件系统级的，不需要改代码或重启

环境变量只从进程环境读取，**永不**从配置文件读密钥。

**第三层：默认干跑。** `execution` 的所有公开方法默认 `dry_run=True`，
返回"将会做什么"的完整描述而不下单。

### 4.2 密钥管理（硬规则）

| 规则 | 理由 |
|---|---|
| 密钥**只**从环境变量读 | 环境变量不落盘、不进 git、不进程间泄漏 |
| 代码中**永不**出现密钥字面量 | 包括测试文件、示例、注释 |
| `.env` 加入 `.gitignore` | 参见 `.env.example`（只有占位符） |
| 日志中**必须**脱敏 | `redact()` 函数过滤 `apiKey`/`secret`/`signature` 等字段 |
| 只授予**必要权限** | 见下 |

**API Key 权限配置（创建时逐条核对）**：
- ✅ 启用现货与合约交易
- ❌ **禁止**「允许提现」（Enable Withdrawals）—— 永远不要勾
- ❌ **禁止**「允许期货转移」（Enable Futures）如非必要
- ✅ **强烈建议**绑定 IP 白名单，只放服务器出口 IP
- ✅ 定期轮换，泄露立刻在币安后台删除

> 密钥泄露的后果是**全部资金归零**，不是"策略失效"。这一节的每一条都不是建议。

### 4.3 风控闸门（`execution/risk.py`）

即使前两层都被绕过，风控层仍独立拒绝：

| 闸门 | 默认值 | 行为 |
|---|---|---|
| 单笔最大名义额 | 200 USDT | 拒绝 |
| 总敞口上限 | 2000 USDT | 拒绝 |
| 单币种敞口上限 | 500 USDT | 拒绝 |
| 24h 最大亏损 | 2% of 总资金 | 触发 → 平仓 + 停机 |
| 最大未对冲敞口时间 | 60 秒 | 超时 → 告警并尝试补腿 |
| 最大基差不利变动 | 0.15% | 基准情景；压力测试另行提高 |

风控参数在 `config.yaml` 的 `risk:` 段，改动会记录到 `logs/audit.log`。

### 4.4 审计日志

所有**下单尝试**（包括被拒绝的）写入 `logs/audit.log`，JSON Lines 格式：

```json
{"ts":"...","event":"ORDER_ATTEMPT","symbol":"BTCUSDT","side":"BUY",
 "qty":0.01,"dry_run":true,"guard_result":"REJECTED","reason":"max_notional",
 "env_checked":"COINTRADER_TRADING_ENABLED=absent"}
```

日志**永不**包含密钥、签名；包含一个 `request_fingerprint`（参数哈希）
用于事后对账但无法反推密钥。

### 4.5 代码级硬约束（测试强制）

`tests/test_safety.py` 静态扫描源码，断言：

1. `data/` 目录下**不存在** `"apiKey"`、`"secret"`、`"signature"`、`"signed"` 等字符串
2. `research/` 与 `backtest/` 下**不存在** `requests`、`httpx`、`urllib` 的 import
3. 全仓库**不存在**硬编码的长十六进制/Base64 字符串（密钥特征）
4. `execution` 层**不被** `data`/`research`/`backtest` import

这些测试失败 = 构建失败。安全约束靠测试保证，不靠自觉。

## 5. 回测方法论

### 5.1 前瞻偏差（lookahead bias）的防治

这是回测最容易骗自己的地方，本项目用**结构性**手段防治：

- **固定滚动历史窗口**：每个时点只使用最近 `backtest.rolling_window_periods` 期数据；
  窗口未满前不生成信号。滚动窗口不是把全样本统计量提前算好。
- **信号与执行分离**：第 t 期信号只能使用 `≤ t` 的数据，成交价使用第 `t+1` 期
  （`execution_lag_bars=1`）或更晚；执行前信号转差则撤单。
- **成本按实际成交入账**：手续费、滑点和基差调整记在真实进/出场时点，
  不按未来持有期事后摊销。
- **动态选币**：组合回测按时间推进，在当前事件可见的候选中排名；已持仓和待成交订单
  都占用 `max_positions`，不能用未来赢家回填早期组合。
- **禁止使用 `shift(-n)`**：`test_no_lookahead.py` 断言代码中不出现负向 shift
- **未来扰动测试**：修改 cutoff 之后的数据，断言 cutoff 之前的信号、账本和组合选择不变。

### 5.2 必须报告的指标（缺一即回测不算完成）

| 指标 | 为什么必须 |
|---|---|
| 扣费后年化收益 | 唯一的结论性数字 |
| **费用占毛收益比例** | > 50% 说明策略在给交易所打工 |
| 最大回撤 | 决定你能否拿得住 |
| 最长连续负资金费期 | 决定资金能撑多久 |
| 基差最大不利变动 | 最坏情况下的额外损失 |
| 盈亏比 / 胜率 | 判断是趋势策略还是噪音 |
| **样本外表现** | 见 §5.3 |
| **破产情景** | 见 §5.4 |

### 5.3 样本内/外分割

时间序列**不能随机分割**（会泄漏）。采用**前推式分割**：

- 前 70% 时间 = 样本内（选币、调参）
- 后 30% 时间 = 样本外（**只看一次**，不许回头调参）

如果样本外表现显著差于样本内，说明过拟合，结论是策略无效。

当前策略阈值是固定配置，`forward_split` 只用于报告诊断，不参与回测信号生成；
组合选币必须使用动态事件回测，而不是先按全历史结果筛选再回放。

### 5.4 破产情景分析（stern scenario）

回测必须回答："如果明天交易所暴雷/停提币/插针爆仓，我会亏多少？"

- 情景 A：永续腿被强平（基差瞬间扩大 20%）→ 损失 = ？
- 情景 B：交易所停提币，资金全锁 → 损失 = 100% 该所资金
- 情景 C：稳定币脱锚（若用 USDC 做抵押）→ 损失 = 脱锚幅度

**因为交易所尾部风险是这类策略真正的杀手**，仓位规模必须按
"这笔钱可能全没"来定，而不是按收益率定。

## 7. 开发里程碑

| 阶段 | 交付物 | 完成判据 |
|---|---|---|
| **M1 数据层** | 能拉取并缓存全市场资金费历史 | 一个命令跑完，数据可复现 |
| **M2 成本与指标** | 成本模型 + 指标计算 | 单测通过，数值手工验算一致 |
| **M3 回测引擎** | 无前瞻回测 | 前瞻证伪测试通过 |
| **M4 扫描器** | 全市场候选排名 | 输出扣费后年化排名表 |
| **M5 结论** | 回测报告 | **回答"值不值得做"** |
| **M6 执行层** | testnet 下单 | 仅在 M5 结论为"值得"时启动 |

**M5 是决策点**。如果扣费后年化 < 5%，项目应在此终止，
而不是继续开发 M6。

## 8. 已知的、不在本框架覆盖范围内的风险

诚实列出，避免虚假的安全感：

1. **交易所单点风险**：框架无法对冲币安自身暴雷。只能靠仓位控制。
2. **API 行为变更**：币安可能改接口。需要监控和快速响应能力。
3. **极端行情下的滑点**：回测用的是历史平均滑点，极端时可能差 10 倍。
4. **强平机制**：永续腿在剧烈波动中可能被强平，导致对冲失效。
   需要保证金监控（框架提供接口，但参数需按实际杠杆实测）。
5. **税务与合规**：不在框架内，但**必须先搞清楚**再投入真金白银。
6. **资金费率的预测性**：历史资金费不保证未来。本框架做的是
   **统计筛选**，不是预测。
