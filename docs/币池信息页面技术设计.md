## 2. 可行性结论

可行。现有代码已经有筛选阶段统计、scan epoch、候选快照、资金费率计算和 WebUI 轮询接口，适合在只读监控基础上扩展。但现有 UI 主要把筛选阶段放在“数据状态”里，尚没有独立币池页面；API 客户端统计以全局计数为主，不能按信息源判断最近成功、失败连续性和数据断流；筛选阶段和候选快照也没有完整投影到 WebUI。

设计重点是把三类状态区分清楚：

1. **限流调度状态**：客户端主动等待预算、排队、软限以上延迟，不属于失败。
2. **请求尝试状态**：网络无响应、HTTP 错误、交易所 API 错误（包括 429/418）属于失败尝试；重试成功也不能抹掉该次失败记录。
3. **信息源健康与数据新鲜度**：最终请求成功不等于整个候选数据集完整或新鲜。分别展示请求健康、最近收到数据时间、epoch 完整状态和各自更新时间。

币池“筛选通过”也不等于“现在可以开仓”。scan epoch 负责形成同一 cutoff 的候选横截面；策略决策还受资金费正向连续期数、成交额、持仓槽位、已有持仓/活动订单、报价新鲜度、账户、对账及安全状态约束。页面要明确区分“池内筛选通过”和“开仓闸门通过”。

## 3. 当前实现核对

### 3.1 WebUI

- `src/cointrader/webui/index.html` 是当前单页控制台，导航以页面锚点组织总览、持仓与 PnL、系统健康、订单与告警。
- 轮询 `GET /api/state`，周期为 3 秒；后端在 `src/cointrader/webui/server.py` 汇总 `LiveService.web_snapshot()`、只读账本数据和健康诊断。
- `market_data.stages` 已渲染为横向阶段条，但位于“数据状态”区，不是独立页面。
- 前端具备 `renderFilterStages()`，阶段字段含输入数、输出数、耗时、更新时间、质量状态。
- 现有 WebUI 不直接请求交易所，页面轮询不应变成额外行情请求。此约束继续保持。

### 3.2 筛选链路

`src/cointrader/live/market_sync.py` 当前阶段为：

| 顺序 | 阶段 | 当前职责 | 统计口径/注意点 |
|---|---|---|---|
| 1 | 合约池 `universe` | 获取 venue 对应的可交易永续交易对 | 输出可交易 universe 数量 |
| 2 | 24h 成交额 `volume_24h` | 获取全市场 24h quote volume，按阈值过滤并按成交额排序，应用候选池上限 | 输入 universe；输出应用阈值和上限后的池。当前代码使用 `min_quote_volume_3d_avg` 作为此处阈值，配置中另有兼容字段 `min_quote_volume_24h`，但当前该字段不是本阶段使用的门槛；页面不得误标成独立 24h 门槛 |
| 3 | 交易规则 `pair_rules` | 通过预检/排除逻辑排除不符合规则的 symbol | 需区分确定性 excluded 与 API/计算失败；异常不能伪装成确定性排除 |
| 4 | 资金费数据 `funding_data` | 按统一 cutoff 获取结算周期、历史资金费并形成 8h 桶快照 | 输入 expected；请求或数据校验失败进入 failed，不算筛选掉 |
| 5 | 资金费信号 `funding_signal` | 依据最近 lookback 窗口的滑动均值年化和连续正费率期数预筛 | 输出需要继续补齐成交额的候选；失败数应独立于策略未通过数 |
| 6 | 3 日成交额 `volume_3d` | 为通过资金费预筛的候选获取闭合 K 线计算的 3 日平均日成交额 | 按 `min_quote_volume_3d_avg` 判定；已开始请求但失败仍进入 failed |
| 7 | READY 横截面 `ready` | 检查 expected 完整性、failed 和 cutoff 不变量后封存 scan epoch | 全部候选有完整快照且无失败才 READY；否则 DEGRADED，不可将部分结果伪装为完整结果 |

阶段状态由 `MarketDataSynchronizer.stage_readiness()` 暴露，字段包括 `input_count`、`output_count`、`duration_ms`、`started_at_ms`、`completed_at_ms`、`updated_at_ms`、`error` 和 `quality`。阶段统计是内存诊断数据，每次开始新 epoch 会重置；账本 `scan_epochs` 持久化 epoch 元数据和候选快照，但没有持久化上述完整阶段耗时明细。

当前 READY 候选快照可由同步器内存 `snapshots_for(epoch_id)` 读取，账本 `candidate_snapshots` 保存资金费历史桶、结算周期、3 日成交额和抓取时间。WebUI 尚未通过专用只读 read model 展示完整候选列表。

### 3.3 费率和阈值

- `src/cointrader/strategy/funding_carry.py` 将资金费历史先归一到 8h 桶，再对最近 lookback 窗口求平均并按 8h 口径年化（`平均 8h 费率 × 24 × 365 / 8`）；入场门槛实际要求 trailing annualized 同时满足 `min_trailing_annualized` 与 `min_annualized_rate`，等价于达到二者最大值。原始合约结算周期仍需显示，但不能对已归一的 8h 桶再次按原周期年化。
- 连续正费率期数也是独立条件，当前配置为 `min_consecutive_positive`。
- 资金费历史经过 8h 桶归一化，epoch 截止固定为 `decision_cutoff_ms`，只允许使用 cutoff 前已发生/已闭合数据。
- `BinancePublicClient.premium_index()` 提供短 TTL 的公开行情响应，其中有交易所 `lastFundingRate` 和下次结算时间；这代表交易所当前费率快照，不等同于已经结算并最终入账的历史费率。
- “当前费率”与“历史平均费率”来源、时间和含义不同，页面必须分别命名，不能混成一个平均值。

## 4. 页面与信息架构

在现有控制台侧导航中增加独立的“币池信息”入口。首期建议采用现有 stdlib WebUI 的 hash 路由/页面视图切换，不引入新前端框架；页面内容分离，保留总览、持仓与 PnL、系统健康、订单与告警等现有工作区。币池页面自身包含三个区块：

1. **API 信息源健康**：每类核心行情数据源一个状态行/表格，持续更新成功、失败、延迟和数据新鲜度。
2. **币池分级筛选**：按 epoch 展示各阶段输入、输出、排除、失败、耗时、状态和最近更新时间；当前运行中阶段显示 RUNNING。
3. **最终筛选候选**：展示当前 READY epoch 经过资金费率和流动性筛选后的候选及费率门槛、差值和数据时间。

页面顶部同时显示 venue（demo/mainnet）、epoch id、epoch 状态、cutoff、开始/完成时间、整体数据年龄及错误/不完整原因。venue 必须从现有 `execution.mode` 推导并明确展示，不能由用户另行配置；demo 与 mainnet 候选池不可混用。

币池页始终只读。不增加触发刷新、强行开仓、修改阈值或调整限流器的 UI 命令。刷新由现有后台同步器调度。无数据、服务停止或诊断不可用时显示 `UNKNOWN`/`UNAVAILABLE`，不显示为 `0` 或“健康”。

## 5. API 健康监控设计

### 5.1 信息源分组

第一版按筛选所需的逻辑信息源分组，至少覆盖：

| 信息源 | 典型接口/功能 | 关注的数据时间 |
|---|---|---|
| 合约清单与交易规则 | `exchangeInfo`、交易对规则预检 | 清单快照更新时间/缓存新鲜度 |
| 24h 成交额 | 全市场 ticker 24h | 最近一次成功响应时间 |
| 资金费结算周期 | `fundingInfo` | 最近一次成功更新及周期数据年龄 |
| 历史资金费 | `fundingRate` 分页、资金费区间仓库 | 请求成功时间、最新结算时间、覆盖/缺口状态 |
| 3 日成交额 | 已闭合 4h K 线及历史覆盖仓库 | 最新纳入 K 线闭合时间、成功时间、窗口完整性 |
| 当前资金费快照 | `premiumIndex` | 最近响应时间、交易所 `nextFundingTime`、费率观测值时间 |

接口分组应保留 scope（Spot/Futures）和脱敏的端点类别；不得在浏览器暴露认证 URL、API key、签名、代理地址或完整错误响应。

### 5.2 失败与等待定义

这是验收口径：

- **不算失败**：本地限流协调器在发出请求前主动排队、软限保护等待、预算等待；没有发出网络请求的本地调度时间不能增加 API 失败数。此时间仍可作为 `throttled/wait_ms` 单独诊断。
- **失败尝试**：请求已尝试发出但超时/网络错误、没有收到响应、HTTP 非成功状态、交易所错误响应（包括 429/418）、响应解析失败或必要字段/数据完整性校验失败。
- **重试成功**：成功结束该次逻辑获取，但前序失败尝试仍要计入错误/重试统计并显示近期错误；不能把 API 限流错误隐藏成零失败。逻辑获取最终状态可为 `RECOVERED`，而不是把全部尝试混为全失败。
- **有效空结果**：按接口契约允许的空列表/稀疏结果不自动等于 API 故障；需要端点级语义验证。比如资金费周期接口可能只列出非默认周期。应将“HTTP/解析成功”和“业务数据是否满足筛选覆盖”分别展示。
- **新鲜度失败**：请求一直成功但数据未按该源的合理更新周期到达，属于数据源 `STALE`/断流风险，不应篡改成 HTTP 请求错误；但候选 epoch 不能因此被报告为完整、可用。

### 5.3 建议的健康字段和状态

每个信息源维护轻量健康快照：

- `source_id`、显示名、market/scope、状态、状态原因；
- `last_attempt_ms`、`last_success_ms`、`last_failure_ms`、`last_data_event_ms`；
- 最近成功获取耗时、上次调度等待时长；
- 当前连续失败数、最近窗口（建议 5 分钟/1 小时）请求数、失败数、429/418 数、重试数；
- 最近一次错误分类/脱敏摘要；
- 数据年龄、预期更新周期、freshness；
- `as_of_ms`、source 和质量标记。

建议状态：

- `HEALTHY`：最近逻辑获取成功，失败率和数据年龄在配置/端点预期范围内。
- `DEGRADED`：有重试、短时错误、较高失败率、数据年龄接近阈值或可恢复错误。
- `DOWN`：连续失败达到门槛、无响应持续超限、429/418 熔断，或核心源超过断流阈值。
- `STALE`：请求面近期可能成功，但产出的数据或结算时间已超过该源的允许年龄。
- `UNKNOWN`：服务未运行、尚无样本或采集器不可用。

阈值应针对每个 endpoint 类别及刷新周期配置/推导，不用一个固定秒数判断所有信息源。页面需显示状态判定原因和 last success，不能只显示绿色图标。

### 5.4 观测实现边界

当前 `ClientStats` 主要是客户端全局计数，没有 endpoint 级成功/失败时间序列。建议在统一 HTTP 请求/响应与 JSON 解码边界增加按端点类别的进程内观测器；API 客户端负责请求尝试和响应分类，筛选器负责数据完整性/业务质量事件，epoch 同步器负责断流和横截面完整性判定。观测器只读导出快照，不改变限流、重试或交易调度行为。

浏览器轮询 WebUI 只读取最近的内存健康快照和只读数据投影，不触发币安 API 请求。第一版可只保留进程运行期计数与有限最近事件；若要求进程重启后查看连续历史，再单独设计持久化保留周期，不把高频健康点无限写入 SQLite。

## 6. 分级筛选指标

阶段表每一行显示：阶段名称、状态、开始/结束/更新时间、耗时、输入数、输出数、确定排除数、失败数、错误摘要。失败/排除/未通过要分开计数：

- **输出/通过**：成功得到下一阶段输入的币对。
- **确定排除**：按明确业务规则被筛出的币对，带原因分类。
- **失败**：信息源无法响应、交易所拒绝/限流、解析错误、数据不完整/滞后等，不得计成“筛选掉”。

筛选链的阶段统计应该满足可核对的数量关系。例：阶段 `input = output + excluded`，其中 failed 要按实际处理策略单列，不能双重计数；若一阶段部分请求失败，显式说明该阶段是否只报告已完成的输出以及 epoch 是否 DEGRADED。对并发候选阶段显示完成/期望数，不能把尚未完成当成筛选不通过。

READY 才表示完整可排名的 epoch。BUILDING 显示当前进度；DEGRADED 显示失败币对数和原因；EXPIRED 显示过期原因/时间；没有 epoch 显示 UNKNOWN。有限 stage 诊断不等同于筛选历史，应显示其更新时间和是否 stale。

### 需要在实现前确认/处理的现状差异

**已确认的筛选顺序决定**：首版保持当前执行链顺序，不把资金费搬到最后一步。用户已选择“保持现状”；本次只定义币池页面与可观测性，不改变筛选规则或请求负载。当前先做 `funding_signal` 预筛，再为通过者获取精确 `volume_3d` 并检查流动性，最后封存 READY epoch。页面如实展示实际顺序，并将 READY 候选定义为通过资金费与 3 日成交额规则的最终池；可以按资金费年化排序，但不得把排序顺序说成执行阶段顺序。

目前 `volume_24h` 阶段将 `min_quote_volume_3d_avg` 应用于 24h ticker，后面 `volume_3d` 阶段又将它应用于 3 日平均日成交额；配置的 `min_quote_volume_24h` 被标为兼容字段。技术实施不得悄悄将 UI 门槛写成一个并不存在的独立 24h 配置。首期应在页面披露“24h 初筛使用当前代码中的配置值”，并将拆分/废弃门槛字段列为单独策略配置决策，不在纯可观测性改动中改筛选语义。

## 7. 最终候选与费率表

### 7.1 候选范围

列表默认展示当前最新**完整 READY epoch** 中已经过资金费信号和 3 日流动性筛选的候选。状态列标明 `READY`、epoch id 和 cutoff。BUILDING/DEGRADED 的部分结果可以在单独诊断区查看，但不能与 READY 候选混排或误称为可开仓池。

当当前 epoch 已过期时，旧候选可以留作历史上下文，但必须标为 `EXPIRED/STALE`，不可显示为当前可用池。进程刚启动而无 epoch 快照时显示“暂无完整候选”，不是空池或 0 个优质币。

### 7.2 候选列

首期表格至少包含：

| 字段 | 定义 |
|---|---|
| 交易对 | venue 中的 USDT 永续 symbol |
| 当前资金费率 | `premiumIndex.lastFundingRate` 的交易所响应费率快照；展示交易所响应时间/本地接收时间、下次结算时间。准确标注为“当前响应费率”，不要直接称“预测费率”或保证它是最终结算值 |
| 最新已结算单期费率 | funding 历史中最近可见的结算费率，可帮助区分实时快照和已结算事实 |
| 平均费率 | 最近 `lookback_periods` 个 8h 归一桶的算术平均单期费率；明确显示 8h 桶口径 |
| 滑窗年化均值 | 策略实际用来比较入场门槛的 trailing annualized，先以原始结算周期归一成 8h 桶，再按 `平均 8h 费率 × 24 × 365 / 8` 年化 |
| 入场门槛 | 展示 `min_trailing_annualized`、`min_annualized_rate` 和有效门槛 `max(...)`；百分比年化口径 |
| 距离费率门槛 | `max(有效门槛 - trailing年化均值, 0)`；若低于门槛显示还差多少，达到门槛显示“已达到”及超出值 |
| 连续正费率期数 | 当前连续正向滑窗期数 / `min_consecutive_positive` 要求 |
| 3 日平均日成交额 | USDT/日及配置门槛，显示通过/不通过 |
| 开仓资格 | 明确区分费率/币池通过与开仓全闸门；展示剩余阻挡原因，如槽位、已持仓、无新鲜报价、账户或对账门禁 |
| 数据更新时间 | funding 快照抓取时间、费率当前快照获取时间、3 日成交额窗口截止时间；不能只给一个含义不明的更新时间 |

对“距离开仓还有多少距离”，至少需显示距离年化费率门槛和连续正期数门槛；只用当前单期费率与门槛相减会误导，因为策略依据滑窗平均年化和连续期数，不是单次当前费率。若币已通过费率筛选但仍未达到连续期数、成交额或其他策略门槛，应逐项给出尚缺条件。所有百分率必须说明 `单期`、`8h 平均` 或 `年化` 口径。

表格默认按滑窗年化均值降序；支持 symbol 搜索、排序和状态筛选。移动端可横向滚动数据表或将行内容折叠为可读的定义明确字段，不压缩成不可辨识的小字。数据规模较大时采用分页/虚拟化，不能把几百币全塞进一次大型 DOM 重绘。

### 7.3 实时费率请求与限流

`premiumIndex` 当前 TTL 为数秒且可批量读取全市场数据；实现应优先复用服务已有缓存/现有计划性请求，避免在每个 WebUI 页面轮询时按币逐个请求。若当前运行链路未定期获取 premiumIndex，应由候选数据刷新调度负责有界批量更新，并归入现有优先级/共享限流器；调度等待不是失败，真实请求错误按第 5 节规则记录。请求增加前应核算权重与请求频率，不能通过降低核心 P0/P1 预算换取 UI 更新。

费率 UI 刷新频率不代表交易策略刷新频率。呈现数据携带自己的 `as_of` 和 freshness；新的 premiumIndex 费率不应更新 funding 历史 epoch 的 cutoff，也不能导致回测/历史候选快照被覆盖。

## 8. Web/API 数据契约

建议新增只读 `GET /api/pool`（或在 `/api/state` 中增加隔离的 `pool` projection；实现时优先考虑减少旧接口负担和兼容现有消费者）。无论采用何种 URL，前后端契约需版本化并只提供 JSON-safe Decimal 字符串/整数时间戳。

响应结构建议：

```json
{
  "as_of_ms": 0,
  "venue": "mainnet",
  "epoch": {
    "id": "ep-...",
    "status": "READY",
    "created_ms": 0,
    "completed_ms": 0,
    "decision_cutoff_ms": 0,
    "age_ms": 0,
    "reason": ""
  },
  "api_sources": [
    {
      "id": "funding_history",
      "status": "HEALTHY",
      "attempts_window": 0,
      "failures_window": 0,
      "consecutive_failures": 0,
      "retries_window": 0,
      "rate_limit_errors_window": 0,
      "last_attempt_ms": null,
      "last_success_ms": null,
      "last_failure_ms": null,
      "last_data_event_ms": null,
      "last_error": null,
      "data_age_ms": null,
      "as_of_ms": 0
    }
  ],
  "stages": [],
  "candidates": [],
  "quality": "OK"
}
```

该结构为设计示意，不是现有 API。精确字段应在实现时与现有 `build_payload()` 一起收敛，避免重复保存相互矛盾的状态。

数据读取路径：

1. LiveService 提供只读运行期健康、venue 和同步器快照。
2. 候选历史快照由同步器 READY 快照或 `LedgerQueryService` 的只读查询获取；WebUI 不直接写账本，也不访问交易所客户端。
3. `premiumIndex` 实时费率经计划性数据采集更新，Web 请求只读最近快照。
4. 任何子区块失败都应局部降级并附 error/quality，不能使其余页面或 live 主循环失败。

账本 `candidate_snapshots` 当前不含完整阶段执行历史，也没有经 `LedgerQueryService` 暴露候选快照列表的查询方法。若要 WebUI 服务重启后仍恢复最新币池，首期应增加受控的只读查询投影，读取最新 READY epoch 的 metadata 和候选 snapshots；不要让 `webui/server.py` 绕过查询端口直接查询 SQLite 原始表。

当前 `CandidateSnapshot` 的 `quote_volume_3d_avg` 默认值可能是 `0`，但候选在资金费预筛未通过时可能根本没有请求精确 3 日成交额。因此 API 投影须同时返回 `volume_status`（至少 `NOT_REQUESTED`、`FETCHED`、`FAILED`）和数值；只有 `FETCHED` 才显示数值并参与门槛判断，不能把默认 `0` 当作有效成交额。

## 9. 并发、安全与架构约束

- WebUI 保持只读，网络/数据刷新在现有 market-data 后台线程或专门的数据采集 owner 内运行。
- 浏览器请求不得触发 Binance 请求、强制 epoch 刷新、费率历史补抓或下单。
- 阶段快照和 API 健康快照在锁内复制后再序列化；不能让 HTTP handler 持锁渲染整个大候选池。
- 请求错误和候选错误进行脱敏、长度限制，不能把 API 凭证或完整请求 URL写到 Web响应。
- 新缓存键遵守 `ckey()` venue 隔离规则；不得把 demo 候选快照标成主网或交给回测。
- 不改变现有 fail-closed 行为：epoch 非 READY、数据 stale、候选信息失败时禁止新开仓；WebUI 降级本身不改变策略安全状态。
- 页面任何地方不把未知计数/时间显示为 0；`null` 必须解释为 UNKNOWN/尚未采集。

## 10. 实施拆分建议

### 第一小步：只读页面与现有阶段数据

建立独立币池页面视图；展示当前 epoch、筛选阶段数量/耗时/状态/更新时间及可从 READY snapshot 得到的费率指标。未能取得的字段明确标 UNKNOWN，暂不伪造 API 健康状态。

### 第二小步：API 信息源健康采集

在请求与解码边界加入按 endpoint 类别的 attempt/operation 观测和健康快照；验证主动调度等待、429/网络错误、重试成功、成功但数据 stale 的分别计量；页面展示窗口计数和 last success。

### 第三小步：当前费率、差距及持久化恢复

为候选集合安全取得/复用 premiumIndex 快照，增加明确的费率字段、门槛差和开仓阻挡原因；把候选只读查询纳入 `LedgerQueryService`，验证 WebUI 服务重启后可读取最近完整 READY epoch。每一步独立测试和上线，不顺手调整筛选参数或交易策略。

## 11. 验收标准

### 页面验收

- WebUI 导航存在独立“币池信息”入口，币池内容不再与总览/持仓/PnL/订单告警混成一个长页面。
- 页面顶部可确认 venue、epoch 状态、cutoff、最近完成时间和数据年龄。
- 筛选各阶段展示输入、输出、排除、失败、耗时、最近更新时间；RUNNING、FAILED、DEGRADED、STALE、UNKNOWN 具有不同且清晰的状态。
- 最终候选表展示当前费率、最近已结算费率、平均单期费率、滑窗年化、有效门槛、差距、连续正期数、成交额门槛和分别标注的数据更新时间。
- 页面清楚说明“筛选通过不保证已具备开仓资格”，给出未满足开仓条件的原因。
- 服务停止、无 READY epoch、数据缺失、API 诊断异常时无误导性 0 或绿色健康状态。
- 桌面和窄屏下字段可读、布局无重叠；大量候选不会引起明显阻塞。

### API 健康验收

- 本地主动限流等待不会增长 API 失败计数，也不会显示为 API 故障。
- 发出的请求遇到 HTTP 429/418、网络错误、超时、HTTP 错误和解析错误均计为失败尝试，并可按源查询。
- 429 重试后成功时，逻辑请求显示恢复/成功，但失败尝试和重试次数保留；最终连续失败数依约定复位。
- 请求成功但业务数据过期/结算延迟/横截面不完整时，API 响应健康与数据 freshness/epoch quality 分别显示。
- 用户浏览器多次轮询 `/api/pool` 不增加交易所 API 请求数。
- 数据源错误不泄漏密钥、签名、完整认证 URL，不阻断交易主循环。

### 自动化测试

- `tests/test_webui.py`：池页面路由/投影序列化、UNKNOWN 和局部失败降级。
- 新增健康观测器测试：成功、未发请求的限流等待、429、网络超时、重试后成功、连续失败、过期数据、未知源。
- 筛选阶段测试：数量关系、失败不算排除、READY 与 DEGRADED 展示一致、stage 时长/更新时间。
- 候选费率测试：不同结算周期年化、最新已结算与当前响应费率字段分离、门槛差为零/正、正期数不足、3 日成交额未请求/获取成功/请求失败状态。
- 验证在币池页面改动中 `tests/test_safety.py`、`tests/test_no_lookahead.py` 仍通过；回测仍固定使用 mainnet 历史。
- 完成改动后执行仓库规定的 `uv run pytest`、`uv run ruff check .`、`uv run mypy` 和 `uv run cointrader doctor`。

## 12. 明确不在本阶段范围内

- 调整资金费年化门槛、连续正期数、流动性门槛、持仓上限或策略排序。
- 修复所有数据源/网络稳定性问题；首阶段提供可定位的真实诊断面板，但具体故障修复按后续工作包处理。
- 新增自动开仓、人工下单、撤单、参数编辑、手动强制刷新等操作入口。
- 重写整个 WebUI 技术栈、引入新服务/消息队列或全面重构数据层。
- 将 Demo 的数据、缓存或币池合并进 mainnet/backtest。

## 13. 主要设计风险

1. **把限流等待误报为失败**：必须在请求 permit 前后定义事件边界，只统计实际发出的请求尝试。
2. **把成功 HTTP 响应误当完整健康**：源健康、解析有效性、数据新鲜度和 epoch 完整性分别表示。
3. **平均费率口径不一致**：实时 `lastFundingRate`、最近已结算单期费率、8h 平均和年化滑窗均值是不同指标，必须分列并注明时间/周期口径。
4. **混淆筛选候选与开仓候选**：保留池是扫描阶段结果；策略仍有连续费率、槽位、价格、账户、对账和安全门禁。
5. **阶段数值语义失真**：现有 24h volume threshold 字段复用存在配置命名差异，页面须照实披露，门槛语义调整应作为独立决策。
6. **诊断数据只驻留内存**：阶段耗时目前不会跨进程恢复；如服务重启后需历史阶段回看，须增加明确的持久化设计和保留策略。
7. **健康展示增加请求负担**：使用批量/已有请求和共享协调器，禁止按币池列表逐条轮询实时接口。
8. **候选值缺少采集状态**：当前 snapshot 的成交额字段无法单凭零值区分未采集与零成交额；投影需增加明确采集状态，禁止把默认零渲染为真实值。
9. **费率时间语义不足**：`nextFundingTime` 是结算时点，不是 `lastFundingRate` 数值的更新时间；必须以本地响应接收时间或可信交易所响应时间标记费率快照。

### API 健康验收补充

- 调度器等待、HTTP 接收时间和数据业务时间各自有独立字段，页面不把 `nextFundingTime` 当成费率更新时间。
- 成交额状态区分未请求、请求成功和请求失败；`0` 只有在成功取得有效数据且语义确为零时才作为数值展示。
