# CoinTrader 7 天 Demo Trading 试运行任务规划

## 1. 目标与结论

目标：在币安 Demo Trading 上进行一次可审计的 7 天试运行。运行期间：

- 策略按配置产生真实的开仓/换仓/退出决策，不用人为降低阈值制造交易；
- 每笔交易、每条腿、每次成交、手续费、资金费、对账、风控判定和异常都落盘；
- 随时可查看当前持仓、订单、交易历史、账户快照、累计收益和运行状态；
- 结束时生成完整数据包，使 AI 能根据事实数据生成报告，而不是根据日志猜测；
- 试运行结束前不进入主网，不提高杠杆，不自动放大名义额。

### 当前结论

**策略的研究/回测实现有基础，但实盘策略还没有真正实施完成。** 当前运行中的 `cointrader-m4` 只验证了 Demo API、代理、轮询用户流和周期对账，不能证明策略能够交易，也不能证明收益计算正确。

当前距离目标不是“再跑 7 天”这么简单，主要还差：

1. **策略信号接线**：`cmd_live_run -> build_live_context` 没有注入 `signal_provider`，当前服务永远不会开仓。
2. **实时策略适配器**：`FundingScanner` 是低频研究扫描器，尚未转换成实时、无前视、去重的开仓/退出决策。
3. **真实风控状态**：默认 `risk_state_fn` 的 `total_capital=0`，真实开仓会被风控拒绝；必须从交易所账户快照构建资金、持仓、未实现盈亏和已实现损益状态。
4. **退出编排**：`LiveService.run_once()` 目前只处理开仓 `Signal`，没有把回测中的负资金费退出、最长持仓、换仓规则接到 `PairExecutor.close_pair()`。
5. **重复开仓保护**：当前 `active_pair_for_symbol()` 只阻止未终态 pair；已完成开仓后，重复信号仍可能再次开仓。必须按实际持仓、策略目标和运行期 intent 去重。
6. **收益归集**：账本已有 `fills`、`position_snapshots`、`account_snapshots` 表，但当前没有形成可查询的实时 PnL 账本；资金费、手续费、基差收益、未实现 PnL、已实现 PnL 尚未统一归集。
7. **查询和报告出口**：当前主要是日志和 SQLite 内部表，没有 `status/history/pnl/report` 等稳定 CLI，也没有 7 天运行数据包。
8. **启动预检范围过窄**：当前只对排序后的第一个共同 symbol 检查/设置杠杆和保证金模式；实际候选 symbol 必须逐个检查。`positionSide=BOTH` 也必须成为显式预检项。
9. **Demo 环境限制**：现阶段只能使用 `user_stream_mode=poll`。成交发现延迟、用户流能力和 `demo-fapi.binance.com` 的非官方性质必须写入最终报告；这不是主网等价验证。

### 7 天试运行能证明什么

能证明：在固定 Demo 环境、固定配置和当前网络条件下，策略信号、双腿执行、成交记录、对账、重启恢复、收益归集和运行报告是否形成闭环。

不能证明：7 天样本足以证明策略长期盈利；7 天内可能没有符合门槛的信号，也可能没有自然触发退出。没有交易是策略忠实执行的结果，不得通过降低阈值伪造交易样本。必要的开平仓链路应使用受控的 Demo 演练完成，不能把演练结果冒充策略收益。

## 2. 验收目标

### 2.1 运行目标

- 固定 Demo 配置、策略版本、代码版本和配置摘要；运行开始和结束时间可追溯。
- 单实例运行；数据库、审计日志、结构化日志可持续写入。
- 每次主循环都能判断：`RUNNING`、`RECOVERY`、`HALTED` 或 `STOPPED`，状态变化有原因和时间。
- 所有开仓前都有新鲜行情、资金费策略快照、风险判定和唯一 intent。
- 所有订单都能通过 `pair_execution_id -> intent -> order -> fill` 关联到一笔交易。
- 任何未知订单、未知成交、裸腿、对账差异、账户查询失败都禁止新增风险并告警。

### 2.2 交易明细目标

每笔 pair 至少记录：

- `pair_execution_id`、交易类型（open/close）、symbol、策略版本、原因；
- 信号时间、决策时间、提交时间、交易所确认时间、完成时间；
- 触发时的资金费率、资金费结算周期、10 期/30 期均值、连续正费率期数、候选排名；
- Spot/Futures 两腿的订单请求、client order id、exchange order id、订单状态变化；
- 每次实际成交的 trade/fill id、数量、价格、成交额、手续费资产和手续费金额；
- 目标名义额、两腿实际名义额、hedge ratio、残余数量、滑点和基差；
- 账户余额、可用余额、Futures 钱包余额、未实现 PnL、保证金相关字段；
- 资金费收入/支出、交易手续费、基差变化、已实现 PnL、未实现 PnL、净 PnL；
- 对账结果、风控判定、异常、重试、补偿和平仓结果。

### 2.3 查询目标

新增稳定 CLI。具体命令名可按现有 CLI 风格实现，但功能必须覆盖：

```text
cointrader live status       当前服务、账户、最近对账、流新鲜度、风险状态
cointrader live positions    当前策略持仓、两腿数量、名义额、hedge ratio、未实现 PnL
cointrader live orders       当前/历史订单及状态
cointrader live trades       pair 交易历史、两腿成交和手续费
cointrader live pnl          当前累计 PnL 分解
cointrader live report       导出运行中或已结束的报告数据包
```

输出至少支持终端摘要和 JSON；CSV/JSONL 用于完整导出。查询命令必须只读，不得触发下单、撤单、杠杆变更或配置写入。

### 2.4 完成条件与硬约束（v2 补充）

- **Demo poll 限制**：demo 用户流不可用，`user_stream_mode=poll` 有成交感知延迟；
  所有“新鲜度”结论必须基于 poll 周期口径，报告不得把 poll 延迟归因于策略；
  7 天样本不得外推为年化策略结论。
- **禁止 fixed wait**：任何“等满 N 秒再继续”的固定等待实现不得作为就绪判据；
  就绪一律基于状态信号（epoch READY、用户流新鲜、对账通过、账户完整）。
- **实际资金费接口可用性证据**：M4/交付报告必须附 `/fapi/income`（FUNDING_FEE）
  在 demo 环境的可用性证据（至少一条真实 income 行或明确的 400/空响应记录）；
  不可用时 authoritative 部分停止并如实报告，不得用估算冒充实际。
- **v2 交付完成条件**（全部可测试，见实施计划书 v2.0 第 8 章矩阵）：
  1. 共享限流协调器：同 scope 公开+签名共享预算、优先级保留、429 冻结、
     418 全停（离线故障注入）；
  2. scan epoch：READY 前无排名开仓；DEGRADED/EXPIRED 只减风险；
     cutoff 后结算/新 K 线使旧 epoch 失效；
  3. kill -9/断电恢复：facts 按游标续跑幂等、候选池外持仓恢复、
     current projection 可信、在线/中断时长按 heartbeat 截断；
  4. 资金费 authority：重复恢复零新增、estimated 不混入 authoritative net；
  5. v1→v2 迁移：临时库无损、事务失败可重试、重复迁移幂等；
  6. 全仓阻塞门禁：pytest 全绿（含安全/无前瞻静态扫描）、ruff/mypy/doctor 全绿。
- **未完成前不得声称**：主网等价验证、年化收益承诺、RECOVERY 自动解除、
  全市场自动交易。

## 3. 开发计划

只分为 3 个工作包。每个工作包完成后都要通过对应验收，不能把未完成能力带入 7 天正式计时。

### 工作包一：把策略变成可控的实时交易流程

目标：真实运行时使用与回测一致的策略条件，并能安全开仓、退出和去重。

#### 3.1 实时策略适配器

新增 `live` 层策略协调器，职责不要放进 `execution`：

- 低频刷新候选池和历史资金费数据；不要在 5 秒执行循环中做全市场扫描。
- 缓存每个候选的资金费历史、结算周期、成交量分档和策略计算结果。
- 开仓条件严格复用配置和回测语义：
  - 最近 `lookback_periods` 期平滑资金费率；
  - `min_trailing_annualized`；
  - `min_annualized_rate`；
  - `min_consecutive_positive`；
  - 流动性、排除资产、可交易规则；
  - 进场时重新获取新鲜 Spot/Futures 报价和时间戳。
- `build_signal()` 只负责交易意图校验，不承担资金费策略判断；策略条件必须在协调器中明确记录并传入 `reason`/策略快照。
- 每次决策记录候选及被拒绝原因，避免只记录“开了什么”而不知道“为什么没开”。
- 同一 symbol 在已有真实持仓、未完成 pair、未完成 intent 或本轮已提交时禁止重复开仓。
- `max_positions`、`per_position_weight`、`canary_notional` 同时生效；Demo 初期建议固定一个高流动性 USDT symbol，先完成单 pair 闭环，再开放多 symbol。

#### 3.2 退出和换仓

把回测中的退出语义接入 live：

- 最近 `exit_lookback_periods` 期平均资金费率转负 -> 退出；
- 达到 `max_holding_periods` -> 退出；
- 按持仓年龄应用 replacement premium -> 允许换仓；
- 发生基差、裸腿、账户风险或人工停机 -> 只执行减仓/平仓路径；
- 退出决策必须先写入 `signal_decisions` 或等价表，再调用 `close_pair()`；
- 平仓必须使用交易所实际数量和 Futures reduce-only 语义；平仓后必须再次对账确认两腿归零。

7 天内不为制造交易而降低 `30%` 年化、连续正费率或流动性门槛。若自然条件没有退出信号，结束试运行时执行一次人工确认的统一平仓，并在报告标记为 `manual_trial_flatten`，不归入策略自动退出表现。

#### 3.3 真实风控状态和启动预检

- 从 Spot/Futures 账户快照构建 `RiskState`，至少提供真实 `total_capital`、当前持仓、已实现损益、未实现损益、可用余额和裸腿时间。
- 账户快照失败、字段缺失或资金为 0 时拒绝开新仓，不静默回退默认值。
- 对**所有允许交易的目标 symbol**逐个验证：Spot/Futures 规则、最小名义额、杠杆、`isolated`、`positionSide=BOTH`。
- 预检实际候选，不只检查 `sorted(symbols)[0]`。
- 明确 Demo 当前无法可靠读取杠杆时的行为：显式设置后记录设置结果和限制，不把它描述成“读取并验证”。
- 保留 `RECOVERY` 人工重启门槛。暂不增加自动恢复，避免信号、账本、对账和安全闸门同时变化。

#### 工作包一验收

- 单元测试覆盖实时入场/退出条件、窗口边界、无未来数据、去重和退出优先级。
- 集成测试覆盖：真实账户资金状态 -> 风控通过 -> 一次开仓 -> 持仓期间不重复开仓 -> 退出 -> 两腿归零。
- 重新启动时已有持仓不会重复开仓。
- `signal_decisions` 能解释每次候选的通过/拒绝原因。
- 真实 Demo 只允许在工作包二的账本和报告能力完成后进入正式试运行。

### 工作包二：完整账本、实时查询和 AI 报告数据包

目标：任何时刻可回答“现在有什么仓位、做过什么、赚了多少、为什么做、是否一致”。

#### 3.4 扩展持久化模型

在现有 `StateStore` 基础上扩展，避免只靠普通文本日志：

- `run_sessions`：运行 id、开始/结束时间、代码 revision、策略版本、配置 hash、模式、端点、状态和停止原因；
- `signal_decisions`：每次候选评估的输入、指标、门槛、结果和拒绝原因；
- `pair_executions`：补齐开平仓时间、触发原因、策略快照、目标/实际名义额、hedge ratio、滑点、费用、资金费和净 PnL；
- `orders`：补充 `pair_execution_id`、intent 关联、提交/确认/终态时间、原始状态摘要和失败分类；
- `fills`：补充交易所 fill/trade id、成交额、手续费、maker/taker、交易所时间与接收时间；
- `funding_cashflows`：资金费时间、symbol、数量、费率、资产、金额、来源和是否已对账；
- `position_snapshots` / `account_snapshots`：周期性采样，并保存来源（startup/periodic/reconcile/close）；
- `risk_decisions`、`reconciliation_runs`、`exchange_events`：补齐关联 id、结构化 details 和错误分类。

所有表保持：

- UTC 毫秒时间；金额和数量使用 `Decimal` 文本保存；
- 交易所唯一 id 建唯一索引；重复事件幂等；
- 原始 payload 只保存必要的非敏感字段；禁止 API Secret、签名和完整认证 URL；
- Schema 变化有迁移/版本处理，不能直接依赖删除数据库重建。

#### 3.5 收益计算口径

实现一个基于账本的 live PnL 聚合器，按 pair 和整个运行分别输出：

```text
funding_pnl       已确认资金费净额
trading_fee       Spot/Futures 实际手续费
basis_pnl         两腿进出场成交价格造成的基差损益
realized_pnl      已平仓净收益
unrealized_pnl    当前持仓按最新标记/报价估值
net_pnl           funding + basis - fee + realized/unrealized 的明确口径
cash_delta        账户现金变化，用于和交易所账户快照交叉验证
```

不要混淆：

- 账户权益变化；
- 交易策略 PnL；
- Demo 平台发放资产或 USDC 余额；
- 未平仓浮盈浮亏；
- 已实现收益；
- 资金费和手续费。

每个数字都带 `source`、时间范围和是否已对账标志。发现账本 PnL 与账户快照无法解释地不一致时，报告中标记为差异，不强行修正成盈利。

#### 3.6 周期采样和查询出口

- 每次下单、成交、状态变化立即写账本；
- 至少每 30 秒写账户/仓位/报价快照，与现有周期对账同步；
- 每次资金费结算窗口后拉取并记录实际资金费；
- 查询命令只读 SQLite，默认显示最近 24 小时，可用 `--since/--until/--symbol/--json`；
- `status` 显示最近对账、流新鲜度、当前模式、当前 pair、账户快照年龄和是否允许开仓；
- `pnl` 显示分项小计、总计、未实现部分和最后更新时间；
- `report` 导出完整 CSV/JSONL/JSON，不把终端摘要当作报告源。

#### 3.7 AI 报告数据包

运行结束后固定生成目录，例如：

```text
reports/live/<run_id>/
  manifest.json
  executive_summary.json
  config_snapshot.redacted.yaml
  signal_decisions.jsonl
  pair_executions.csv
  orders.csv
  fills.csv
  funding_cashflows.csv
  pnl_ledger.csv
  position_snapshots.csv
  account_snapshots.csv
  reconciliation_runs.csv
  risk_decisions.csv
  exchange_events.jsonl
  alerts.jsonl
  service.log
  audit.log
  report_prompt.md
```

`manifest.json` 必须列出：运行时间、数据文件、行数、SHA-256、代码版本、策略版本、配置 hash、时区、Demo 端点、数据完整性检查结果。`report_prompt.md` 提供固定报告要求：

- 先报告数据完整性和对账情况，再报告收益；
- 分开已实现/未实现、资金费/手续费/基差；
- 列出每笔交易和异常；
- 解释策略实际使用的入场/退出条件；
- 比较实时实际成交与配置/回测假设；
- 明确 Demo、poll 模式、样本长度带来的限制；
- 禁止把 7 天结果外推成年化结论。

#### 工作包二验收

- 随机选一笔交易，能从报告反查到 signal、pair、两腿 order、每次 fill、费用、对账和 PnL。
- 数据库关闭/重启后查询结果不丢失。
- 运行中执行 `status/positions/pnl` 不影响交易线程，不触发任何写交易 API。
- 生成的数据包无密钥和签名；文件清单、行数、哈希校验通过。
- 用固定 fixture 计算的 PnL 与手工结果一致；重复资金费/成交事件不重复计入。

### 工作包三：受控 Demo 试运行与验收报告

目标：先做短演练，再开始正式 7 天计时；期间不修改策略和关键风控阈值。

#### 3.8 正式计时前演练

按顺序完成并保存记录：

1. `doctor`、网络/代理、server time、Demo 账户、规则、单实例锁和数据库备份检查。
2. 运行 shadow，确认实时候选、策略条件、拒绝原因和预期订单合理。
3. 受控开仓演练：一笔 `canary_notional=10 USDT`，`1x`、`isolated`，确认两腿实际成交和账本链路。
4. 立即执行一次受控平仓，确认 Spot 余额和 Futures 持仓归零。
5. 进程重启演练：有持仓时重启，确认启动对账通过且不重复开仓。
6. 停机文件演练：确认停止新增风险；必要时仍能执行受控 reduce-only 平仓。
7. 失败演练：模拟/fixture 覆盖部分成交、订单响应超时、拒单、查询失败、轮询不可信和数据库写失败。
8. 备份并验证可恢复的 SQLite 数据库和完整报告导出。

演练未通过，禁止开始 7 天正式计时。

#### 3.9 7 天运行规则

- `execution.mode=testnet`，实际端点为 Demo；`user_stream_mode=poll`；固定当前代理策略组；
- 固定代码、配置、策略版本和数据库路径；任何修改先停止新增风险、导出、对账、重启；
- 每日固定检查并记录：服务状态、账户/仓位、对账、未完成订单、流失败次数、信号数、开平仓数、手续费、资金费、PnL、磁盘和日志；
- 每天导出一次增量摘要，结束时导出完整数据包；
- 出现未知订单、裸腿、对账差异、持续 REST 失败、账户字段缺失、数据库/审计写失败、错误模式端点时，立即停止新风险并人工处理；
- 不删除数据库、不清空日志、不覆盖原始报告；
- 7 天内不因为暂时没有信号而降低策略门槛；
- 结束时先停止新信号，完成最终对账；有持仓则人工确认后 reduce-only 平仓，再做最终快照和报告导出。

#### 3.10 正式验收门槛

必须全部满足：

- 连续 7 天无未解释的对账差异；
- 每笔订单都有 intent、pair、order、fill 或明确拒绝/失败原因；
- 没有重复 intent、重复订单、静默裸腿或未确认订单；
- 每次重启都能恢复并完成对账；
- 所有自动/人工开平仓都能从报告数据包重建；
- PnL 分项有来源，账户现金变化与账本差异有解释；
- 所有严重告警都有时间、原因、处理动作和结果；
- `pytest`、`ruff`、`mypy`、安全扫描全部通过；
- 报告能明确区分：策略表现、执行质量、Demo 环境限制、数据缺口和未验证假设。

任何一项不满足，只能结论为“执行观察未通过”，不能称为策略验证通过。

## 4. 策略实施审查结论

当前策略本身不是简单“直接把 scanner 接入 live”即可：

- 回测策略使用滑动资金费率、连续正费率、动态选币、负资金费率退出和持仓年龄换仓；live 必须复用这些规则，否则实盘与回测不是同一个策略。
- `FundingScanner` 当前已经能计算候选的 `trailing_annualized`、连续正费率和流动性，但它不是实时信号系统，不能直接作为 5 秒 provider。
- `build_signal()` 只验证价格新鲜度、名义额和基差，不验证资金费门槛；不能把它误当作完整策略判断。
- 回测默认最长持有 `270` 个结算期。若按 8h 计算，远长于 7 天；7 天自然不一定出现自动平仓。因此“7 天内有自动开平仓”不能作为合理硬要求；必须把“策略自然交易”和“受控执行演练”分开统计。
- 7 天实际 PnL 样本很短，资金费收益可能小于四条腿手续费和基差波动。最终报告不得把短期收益年化后作为策略结论。
- Demo 用户流不可用，当前 poll 模式有成交感知延迟；M4 只能证明在该限制下的执行和对账，不能替代主网 WS 验证。

## 5. 预计距离目标

按代码能力而不是日历时间估计：

- 执行基础、订单状态机、双腿补偿和基础对账：已有较多实现；
- “真实策略自动交易”：约完成 30% 以下，信号、退出、资金状态、去重尚未闭环；
- “每笔交易可追溯”：已有底层表，但关联字段、资金费和统一 PnL 仍不完整，约完成 50%；
- “随时查看当前/历史/盈利”：约完成 10% 以下，CLI 和聚合查询尚未实现；
- “AI 可直接生成可信报告”：约完成 20% 以下，需要运行 manifest、完整导出、数据完整性检查和报告模板；
- “可开始 7 天正式试运行”：当前**未达到**。完成上述 3 个工作包并通过演练后，才达到。

最短可行路径是：先收敛为一个高流动性 symbol、10 USDT、1x isolated、Demo poll 模式，完成一次真实开平仓和重启恢复，再开始 7 天；不要先做全市场自动选币，也不要先做 RECOVERY 自动解除或主网适配。

## 6. 交付后操作命令

## 7. 变更纪律

- 本文件是 7 天试运行的验收基准；代码实现偏离时必须同步更新原因和影响。
- 任何配置变更都记录旧值、新值、时间、操作者、原因，并重新生成配置 hash。
- 不为获得更多交易而放宽入场条件、提高杠杆、关闭对账或忽略异常。
- 不把日志中的“对账通过”解释成“策略盈利”；两者属于不同验收维度。
- 不把 Demo 账户余额、平台发放资产或 USDC 余额变化计入策略收益，除非有明确的成交/资金费来源。
